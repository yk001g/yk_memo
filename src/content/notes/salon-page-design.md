## はじめに：「リンクを貼りたい」、それだけのつもりだった

前々回の記事(4月26日)で、Claude Design と Claude Code を組み合わせて自分のサイト「yk_memo」を立ち上げた話を書きました。前回の記事(4月29日朝)では、その後つまずいた経験から**サイトの設計そのものを作り変えた2日間**の記録を残しました。

今回の記事は、その**新しい設計の上で取り組んだ最初の仕事**——地域活動への動線を引いた話です。

しばらく運用してみて、気になることが出てきました。私は八王子・片倉台で月1回、シニア向けスマホ相談会「スマホ・わいわいサロン」を運営・講師として続けています。その活動が、yk_memoサイトのどこにも載っていない。

「サロンのサイトへリンクを1本貼るだけ」——最初はそう思っていました。ナビゲーションに項目を1個足す、それだけの作業のはずでした。

ところが Claude にそのことを相談したら、想像していたよりずっと深い設計の話になりました。3つの選択肢が出てきて、それぞれにトレードオフがあって、最終的に決まったのは「ハイブリッド方式」というもの。さらにそこから、過去にNotebookLMで作ったPDFを発掘して送ったら、ページの設計図そのものになり、本文の清書、Claude Codeへの引き渡し、実装中の小さな発見——と、半日がかりの仕事になりました。

完成したのは、 `yk-memo.vercel.app/salon/` というたった1ページです。でもその1ページを設計するプロセスには、AIと協働して何かを作るときの**ジグザグした実態**が全部入っていました。

この記事は、その記録です。

---

## 第1章：最初の相談で、3つの案が出てきた

私はまず、Claude（チャット）にこう投げました。

> ここ数日でClaude Design × Claude Codeで、yk_memoというホームページを一緒に作りました。このホームページから私が関与している＜スマホ・わいわいサロン＞のホームページにリンクをはり、yk_memoホームページからも読めるようにしたい。良い案はありますか？

返ってきたのは、3つの案でした。

**A案：シンプル外部リンク方式**——ナビかトップページにカード1枚を作って、別タブでサロンサイトへ飛ばす。実装10分。

**B案：yk_memoサイト内に統合**——サロンサイトのコンテンツを移植して、 `/salon/` ページとして作り直す。ブランド統一感は出るが、二重管理のリスクあり。

**C案：ハイブリッド方式**——yk_memo内に「紹介ページ」を1枚だけ作り、詳細は外部リンクへ送る。

私は最初、A案で十分だと思っていました。リンクが1本貼れれば目的は果たせるはずだ、と。

でも Claude は、こう書いていました。

> 重要な観点：サロンの「主催」をどう扱うか
> スマホ・わいわいサロンは**片倉台自治会・福祉委員会・福祉ネットワーク**の主催で、YKさんは運営として関わっている立場ですよね。そうするとサロンサイトを「yk_memoサイトに飲み込む」のは少し違って、「yk_memoはサロンを応援・運営している」という関係性で外側にリンクするのが自然です。

これを読んだとき、私は「ああ、その通りだ」と思いました。

サロンは私個人のものではありません。片倉台自治会の公式活動です。私はそこで運営と講師を担っているけれど、サロン自体を「yk_memoブランド」に取り込むのは越境です。だからこそ、yk_memo側からは「自分が運営している活動として語る」、でもサロンの本体は外部の自治会サイトに置いておく——その距離感を保つには、C案の「間に紹介ページを1枚挟む」が正解でした。

> 【現場の判断】
> リンクを貼る、という作業は、単に技術的な配線ではない。**リンク先との関係性をどう言葉にするか**という設計判断を含んでいる。私個人のブランドと、地域組織の活動を、どういう距離感でつなぐのか。Claudeはその距離感を最初から押さえてきた。

ここで私は気づきました。Claudeに3案を出してもらったことが大事だったのではない。**3案のうち、なぜC案が正しいのか**を、Claudeが「主催が誰か」という事実から導いてくれたことが大事だったのです。

A案で済ませていたら、外形的にはリンクは貼れても、「サロンは私の活動の一部です」という誤った印象を訪問者に与えていたかもしれません。

> ◎ 第1章のミニまとめ
> 「リンクを貼る」前に、リンク先との関係性を一文で言語化しておく。それが「外部リンクを貼るのか、内部に取り込むのか、間に1枚挟むのか」を決める。


## 第2章：PDFを渡したら、設計が一気に動いた

C案で進めることが決まったあと、Claudeから「サロンとは何か」を yk_memo 視点で書く必要があるという話になりました。300〜400字程度の紹介文を、自分の言葉で。

そのとき、ふと思い出したものがありました。少し前に NotebookLM で作っていた、サロンの活動紹介用の15ページのPDFです。これは**自分自身の振り返り用**と**広報用**を兼ねて作ったもので、サロンの哲学や6つの学びのテーマがまとめてありました。

「これ、使えるかもしれない」と思いついて、Claude に渡してみました。

返ってきた反応が、予想を超えていました。

> このPDFは想像以上に活用できます。`/salon/` ページに必要だった要素が、ほぼすべてこの中にあります。

そして Claude は、PDF の各ページを「ページの設計図」として整理し直してくれました。

- キャッチコピー → 「質問、大歓迎。みんなで学ぶ、スマホの『？』解決の場」
- サロンの説明 → 2ページ目の本文
- 学びの全体像 → 3ページ目の **6つのテーマ**
- 個別の活動内容 → 4〜12ページの具体例
- サロンの哲学 → 13ページ：「主役は懇談タイム。誰もが、生徒であり先生です」
- 開催情報・参加案内 → 14ページ
- 雰囲気の写真 → 1ページ目・15ページ目

つまり、**そのPDFが `/salon/` ページの「設計図」と「素材」を兼ねている**——という指摘でした。

> 【気づき】
> 自分の活動を「自分の言葉で言語化する作業」は、思っているより難しい。普段サロンで口頭で話していることは、頭の中にあっても文字になっていない。NotebookLMで一度PDFにまとめたとき、私は「自分の振り返り用と、広報用に役立つもの」と考えていた。でも数か月後、そのPDFは「ホームページの設計図」として再利用できた。
> **言語化した素材は、用途を超えて再利用できる**。AIに渡したことで、その事実に気づかされた。

これは、AIと協働するときの大事な感覚だと思います。AIは「ゼロから新しいものを作る道具」だと思われがちですが、実は私たちが過去に積み上げた素材を**別の用途に再配線する**のが、とても得意です。

過去のPDF、過去のブログ、過去の講座資料、過去のメモ——それらを「もう古い」と捨てる前に、AIに見せてみると、設計図として蘇ることがあります。

> ◎ 第2章のミニまとめ
> 「素材」と「設計図」は、同じものでありうる。過去の制作物を AI に渡すと、思いがけない用途で再利用できる。捨てる前に見せてみる。

## 第3章：「取り込まない」という設計判断

PDFがページ構成の8割を決めてくれました。これだけ素材が揃っていれば、もはや「内容を全部 yk_memo 内に持ち込んで作り直す」B案でも実装できそうな状態です。

でも、私はその誘惑には乗りませんでした。乗らなかった理由を、ここに残しておきます。

サロンの本拠地は、片倉台自治会のホームページの中にあります。Google Sites で運営されていて、毎月の活動レポートが写真付きで更新されています。たとえば 2026年4月7日の回では、警視庁アプリ「デジポリス」を全員でインストールして、国際電話のブロック設定を実践した——という記録が残っています。

このサイトの更新作業は、私が担当しています。一方、毎月のサロンそのものの運営は、自治会のメンバーと一緒に進めています。**書く責任、編集する権限、写真の許諾**——それらは自治会全体に集約されていて、私はそのなかで運営と講師を担う立場です。

もし私が「PDFの内容を全部 yk_memo に移植する」と決めたら、その瞬間に、私は自治会のコンテンツを個人サイトに**複製する**ことになります。コンテンツの責任が二重になり、更新が片方で起こったとき、もう片方は古いままになる。さらに、写真や参加者情報の扱いも、個人サイト側で別途確認する必要が出てきます。

この煩雑さは、**長期的に見て続かない**運用です。

だから、yk_memo 側の `/salon/` ページは「窓口」に徹することにしました。

- サロンが何を大切にしている場なのか（哲学）
- どんなテーマを扱っているのか（6つの学び）
- 私自身がそこにどう関わっているのか（運営・講師）

——これら、**変化の少ない情報**だけを yk_memo に置く。一方で、**毎月変わる情報**（次の開催日、最新の活動レポート、参加申し込み）は、自治会の公式ページに任せる。

CTAブロックの文言は「最新は公式ページへ」というシンプルな言葉に絞り、外部リンクの矢印アイコン（↗）を添えて、訪問者に「ここから先は別の場所です」と視覚的に伝えるようにしました。

> 【哲学】
> 個人ブランドの活動と、地域組織の活動は、**距離感を保つことで両立する**。一方が他方を飲み込んでしまうと、責任の所在が曖昧になり、長期的には片方が形骸化する。
> 「取り込まない」という選択は、技術的にはなにも難しくない。でも設計判断としては、一番考えるところだった。

私は yk_memo というブランドで活動していますが、それは「私個人のすべて」ではありません。地域には地域の主体があり、私はその一員です。サイトの構造は、その関係性を反映するものでなければいけない。

> ◎ 第3章のミニまとめ
> 「取り込まない」という設計判断は、長期運用を見据えた選択。変化の少ない情報を自分のサイトに置き、変化の多い情報は本家に任せる。これが「窓口ページ」の正しい使い方。


## 第4章：6つのテーマと「サロンの哲学」

C案で進める方針が決まり、PDFが設計図として揃ったところで、ページ全体の構成を一気に固めました。

最終的な /salon/ ページの構成は、こうなりました。

1. **ヒーロー**：「質問、大歓迎。みんなで学ぶ、スマホの『？』解決の場。」
2. **サロンとは**：3段落の本文（2024年4月の開始、参加者数、運営方針）
3. **学びの6つのテーマ**：①毎日の基本操作 ②LINEを徹底活用 ③暮らしと地域を便利に ④安全・安心の備え ⑤趣味と楽しみを広げる ⑥未来の技術に触れる
4. **サロンの哲学**：blockquote として「主役は懇談タイム」を引用
5. **関連する記事**：tag に "salon" を含む Notes を自動表示
6. **CTAブロック**：「最新は公式ページへ」と外部リンク
7. **フッター情報**：主催と運営・講師の表記

この構成のなかで、特に書けて嬉しかったのは「サロンの哲学」セクションでした。

> 主役は「懇談タイム」。
> 学び合い、教え合う、私たちの時間。

これは、サロンで毎回口頭で言っていることです。「今月のワンポイント」を私が15分くらい解説したあと、テーブルごとに分かれて懇談タイムに入る。そこではみんなが質問を持ち寄り、お互いの画面を見ながら解決策を探す。**生徒も先生もない、双方向の学び**——それがサロンの核です。

でも、この「核」を、文字にして固定したのは初めてでした。普段は会場の空気として共有されているだけで、文書化されていなかった。それを yk_memo サイトの blockquote として置いた瞬間、口頭の経験が**読める形のメッセージ**になりました。

> 【哲学】
> サイトに何かを載せる、という行為は、自分の活動の核を**言語化して残す**ことだ。実装技術の話に見えて、実は自己理解の作業でもある。
> Claude や Claude Code は、その「言語化」を急かさず、私の言葉で書くのを待ってくれた。AIは「全部書いてくれる存在」ではなく、「言葉が出てくるのを助けてくれる存在」なのだと思う。

実装より先に、コアの哲学を一文に絞っておく。これは、AIと協働してサイトを作るときの大事な準備です。哲学が決まっていれば、ページ構成もデザインも、自然に従ってきます。

> ◎ 第4章のミニまとめ
> 実装より前に、自分の活動のコアを「一文の引用」にできるか試す。それが書ければ、ページ構成は自然に決まる。

## 第5章：文章を清書する——自分の言葉で

ページ構成が固まったあと、本文の清書に入りました。

ここで一つ、選択がありました。Claude にお願いすれば、6つのテーマの説明文も「サロンとは」の3段落も、全部書いてもらえます。それで完成度の高い文章は出せたはずです。

でも、私は Claude が書いた素案に、自分で手を入れることを選びました。理由は、サロンの紹介文は**自分の声で書きたかった**からです。

具体的に、私が修正したポイントは3つあります。

### ① 参加者数の表記

Claude の素案では、PDFにあった「2024年7月には26名超え」という具体的な数字が引用されていました。でも、もうその数字は古い。最新の正確な数字を出すのも気が引ける（毎月変動があるため）。

そこで、**「最近では1回あたり20名以上の方が参加されることもあり」**という、ぼかした表現に書き直しました。これなら数字が古くなっても、嘘にはなりません。

### ② 自分の立ち位置

Claude は最初、「運営協力：yk_memo」と書いていました。でも、これは違う。私は協力者ではなく、運営まとめと講師を兼任しています。協力してくれるメンバーは別にいる。

そこで、**「運営・講師：yk_memo（協力メンバー数名）」**という表記に変えました。「運営・講師」の2語並列で、私が両方を担っていることを示し、「協力メンバー数名」で支援者の存在も見える化する。

これは Claude が一人で正解にたどり着けない部分です。**現場の役割分担は、現場の人間しか知らない**からです。

### ③ CTAの誘導文言

Claude の素案には「開催日時・場所・参加方法など、最新の情報は片倉台自治会の公式ページでご案内しています」という丁寧な文章がありました。

これを**「最新は公式ページへ」**の一行に絞りました。短い方が、外部リンクであることが直感的に伝わるし、ボタンの存在感が際立ちます。

> 【現場の判断】
> AIが書いた素案を「全部使う」「全部捨てる」の二択にしない。**どこを残してどこを直すかの取捨選択**そのものが、自分のブランドを形にする作業。
> 修正の量で言えば、Claudeが書いた本文の8割は残った。でも、その2割の修正に、yk_memo の声が宿っている。

「AIに書かせる」と「AIに整えてもらう」は、似ているようで全然違う作業です。前者は丸投げ、後者は協働。私は後者を選びました。

> ◎ 第5章のミニまとめ
> AIが書いた素案を「自分の声」で整え直すことが、ブランドを作る。修正は2割でも、その2割が記事のトーンを決める。


## 第6章：Claude Codeへの渡し方——プロジェクト内に置く

本文の清書が終わったところで、Claude（チャット）が「Claude Codeに渡せる詳細プロンプト」を作ってくれました。実装指示が書かれた `claude_code_prompt.md` と、本文が書かれた `salon_page_content_final.md`。この2つのファイルを Claude Code に読ませれば、`/salon/` ページが実装される、という段取りです。

ここで、私は躓きました。

Claude（チャット）の説明はこうでした。

> ターミナルでyk_memoプロジェクトディレクトリに入り、Claude Codeを起動した状態で、この2つのファイルを参照させて指示するのが一番スムーズです。
> 
> ```
> ~/Downloads/claude_code_prompt.md と ~/Downloads/salon_page_content_final.md を読んで、
> プロンプトの指示どおりに実装してください。
> ```
> 
> （ダウンロードしたファイルの実際のパスに合わせて読み替えてください）

正直に言います。**この説明、私には全然分からなかった**のです。

`~/Downloads/` のパスを「読み替えてください」と言われても、何にどう読み替えればいいのか。ファイルは確かにダウンロードしたけれど、それを Claude Code が読みに行く、という発想がそもそも腑に落ちなかった。

私は素直に、こう聞き返しました。

> 「ダウンロードしたファイルの実際のパスに合わせて読み替えてください」の部分がよくわかりません。

すると Claude（チャット）は、その場で説明を全面的に書き直してくれました。

新しい説明では、

- プロジェクト直下に `_instructions/` というフォルダを作る（Astroは `_` で始まるフォルダを無視する）
- そこに2つのMDファイルを置く
- Claude Code には `_instructions/claude_code_prompt.md と _instructions/salon_page_content_final.md を読んで…` と相対パスで指定する

——という、はるかに分かりやすい手順が示されました。

実際にやってみたら、3分で完了しました。

> 【失敗談】
> 私が躓いたのは、私の理解力の問題ではなかった。最初の Claude（チャット）の説明が、**自分の視点に立っていなかった**だけだ。
> 「~/Downloads/ から読み替える」というのは、エンジニアなら自然に通じる表現かもしれない。でも、私のように「Claude Code とプロジェクトとファイルパスの関係」を体系的に理解していない人間には、抽象すぎる。
> 大事だったのは、「**分からない**」と素直に言えたこと。曖昧なまま自分で推測して進めると、間違いなく途中で詰まっていた。

これは、AIと協働するときに何度も思うことです。AIの説明が分からないとき、自分を責める必要はありません。**「分からない」と返せば、AIは説明を作り直してくれる**。それは Claude（チャット）でも Claude Code でも同じです。

むしろ、「分からない」と言えるかどうかが、AI活用の分かれ道だと思います。分からないまま進むと、AIは間違った前提のまま走り続けてしまう。早めに止めて、聞き直す。それが結局、一番速い。

> ◎ 第6章のミニまとめ
> AIの説明が分からないときは、すぐに「分からない」と返す。AIは説明を作り直してくれる。曖昧なまま推測で進めると、必ず途中で詰まる。

## 第7章：Claude Codeが、自分でコードを直しはじめた

`_instructions/` フォルダを作って2つのMDを置いて、Claude Code を起動して指示を投げると、すぐに作業が始まりました。Claude Code の動きを横で見ていて、印象に残った瞬間が2つあります。

### 印象的だった瞬間 ①：自分でコードを書き直した

Claude Code は、まず `/salon/` ページを350行で書き上げました。書き終わったあと、自分の書いたコードを見直して、こう言いました。

> CTAの href に HTMLコメントを入れてしまっているのを修正します。フロントマターに変数として切り出し、コメントと href={} で見つけやすくします。

これは、私が出した指示にはなかった作業です。私は「公式URLが未確定なので TODO コメントを残してください」とお願いしただけでした。

でも Claude Code は、最初に書いた実装を**自分で見直して**、「これだと後から差し替えるとき見つけづらいな」と気づき、変数として切り出す形に整理し直したのです。

これは、人間のプロフェッショナルなエンジニアの振る舞いそのものでした。

### 印象的だった瞬間 ②：私が知らなかったナビ項目を拾った

完成報告のあと、ブラウザで確認すると、ナビゲーションは「Notes / Skills / **Lessons** / サロン / About」となっていました。

「Lessons」？

私はそんなナビ項目があったことを、その瞬間まで意識から外していました。少し前にプロジェクトに加えていたページで、これからどう使うかをこれから考えていこうと思っていたところです。Claude（チャット）に出した実装プロンプトには、ナビ項目として「Notes / Skills / About」しか書いていませんでした。

でも、Claude Code は実際のプロジェクトを読んで、**Lessons が既存のナビにあることを認識した上で**、その間に「サロン」を自然に挿入したのです。

> 【現場の発見】
> Claude（チャット）に渡した指示書は、私の頭の中の不完全な地図に基づいていた。Lessons があったことを忘れていた私の地図には、Lessons は載っていなかった。
> でも Claude Code は、**指示書ではなく実物のプロジェクトを読んで**実装した。だから私の地図のミスを補ってくれた。
> これが Claude（チャット）と Claude Code の役割分担の本質だと思う。チャットは「私の頭の整理」を手伝う相手、Claude Code は「実物のプロジェクトに向き合う」実装者。

この2つの瞬間で、私は Claude Code の使い方が少し変わりました。

これまでは「指示通りに動かす」道具だと思っていました。でも実際には、Claude Code は**プロジェクトの現実を読んで、指示の不足を補ってくれる**存在です。だから指示書を完璧に書こうとする必要はない。骨子を渡せば、細部はプロジェクトの実物を見て埋めてくれます。

> ◎ 第7章のミニまとめ
> Claude Code は、指示書ではなくプロジェクトの実物を読む。だから指示が完璧でなくても、現実のコードに合わせて実装してくれる。指示書を完璧にする努力より、プロジェクトを綺麗に保つ努力の方が効く。


## 第8章：ローカル確認 → GitHub Desktop でプッシュ

Claude Code から「実装完了」の報告が出たあと、ブラウザで `http://localhost:4321/salon/` を開きました。

仕上がりは、想像以上でした。

ヒーローの「質問、大歓迎。みんなで学ぶ、スマホの『？』解決の場。」が、yk_memoサイトのベージュ背景に大きなタイポグラフィでバチッと決まっています。6つのテーマカードはデスクトップで3列、タブレットで2列、モバイルで1列に綺麗に並ぶレスポンシブ。サロンの哲学の blockquote は左の縦線が効いていて、引用らしさが伝わる。CTAブロックは薄緑の囲みに青いボタン、外部リンクの「↗」マーク付き。

ナビには「Notes / Skills / Lessons / **サロン** / About」が並び、サロンのページにいるときだけ「サロン」が現在ページとして強調される。

About ページにも、サロン運営の段落が追加されて、`/salon/` への内部リンクが効いている。

すべてが、想定どおり——いや、想定の少し上で動いていました。

最後に1つだけ、公式URLの差し込み作業が残っていました。Claude Code は、URL未確定の状態で `<!-- TODO: ... -->` のコメントを残してくれていました。私は片倉台自治会の公式ページのURLをコピーして、`src/pages/salon/index.astro` の上部にある `const salonOfficialUrl = '';` の空欄に貼り付けました。

これで完成。

あとは GitHub Desktop でコミットしてプッシュするだけです。

GitHub Desktopの画面を開くと、変更されたファイルが一覧されていました。

- `src/pages/salon/index.astro`（新規）
- `src/layouts/BaseLayout.astro`（編集：ナビに「サロン」追加）
- `src/pages/about.astro`（編集：サロンへの内部リンク）
- `_instructions/` 内のMDファイル2つ（新規：今回のプロンプトと本文）

Claude（チャット）からの提案に従って、`_instructions/` フォルダもコミットに含めました。これは「将来同じような追加をするときのお手本」として、自分のプロジェクト内に手元に残しておきたかったからです。

コミットメッセージを書いて、Push origin。1〜2分で本番反映されました。

> 【気づき】
> 完成までの最後の一押しは、シンプルなのが良い。複雑なデプロイ手順を踏もうとすると、それだけで気が重くなる。GitHub Desktop の「コミット → プッシュ」のたった2ステップで本番に反映される、という設計が、続けやすさを生む。

> ◎ 第8章のミニまとめ
> 動作確認は「ブラウザで実際に開く」が基本。本番反映は「コミット → プッシュ」の2ステップに収める。続けやすさは、最後の一押しの軽さで決まる。

## 第9章：3ツールの役割分担を振り返る

ここまで読んでくださった方には、もう見えていると思います。今回のプロセスは、3つのツールの役割分担で動いていました。

### Claude（チャット）：相談相手・設計者・文章編集者

最初に「リンクを貼りたい」と相談した相手です。3つの案を出し、サロンの主催が誰かという事実を踏まえて C案を勧め、PDFを「設計図」として読み解き、本文の素案を書き、Claude Code 用のプロンプトを準備しました。

つまり、**実装する前の「考える時間」をすべて担当**したのが、Claude（チャット）でした。

### Claude Code：実装担当・プロジェクトの現実を読む

プロンプトと本文MDを受け取って、実際にコードを書いた相手です。Astro の構造を理解して、`/salon/` ページを作り、ナビゲーションに「サロン」を追加し、About ページに内部リンクを足しました。

そして、私（チャット）が把握していなかった「Lessons」項目を**自分で発見して**、自然な位置にサロンを挿入しました。CTAのコードを書いたあとに「これは変数に切り出した方が見つけやすい」と自分で整理し直しました。

つまり、**プロジェクトの実物に向き合う時間**を担当したのが、Claude Code でした。

### GitHub Desktop：本番への扉

コミットメッセージを書いてプッシュするだけ。それ以上でも、それ以下でもありません。

つまり、**本番反映の最後の一押し**を担当したのが、GitHub Desktop でした。

---

この3ツールが、それぞれ「越境しない」ことが、結果として効率を生んでいました。

もし Claude（チャット）が実装まで踏み込もうとしたら、プロジェクトの実物を見ずに想像で書くことになり、必ず細部でズレます。もし Claude Code が設計判断まで担当したら、プロジェクトのコードしか見えていないので、「サロンの主催が誰か」のような外部の文脈を見落とします。もし GitHub Desktop が複雑な機能を持っていたら、本番反映が億劫になります。

それぞれが**自分の持ち場に集中する**から、全体としてスムーズに回る。

> 【哲学】
> AIは「万能の道具」ではなく、**役割を持つ複数の道具**として使う方が、結果として早い。
> 1つのAIに全部やらせようとすると、必ずどこかで無理が生じる。3つに分業させる方が、それぞれの強みが出る。
> これは、人間のチーム運営とまったく同じ原理だ。

私はサロンで「AIと競争しない」と言っています。今回のプロセスを振り返って、それは「AIに全部やらせない」ということでもあるのだと、改めて思いました。**AIを使いこなす**とは、**AIに何をやらせないかを決める**ことなのです。

> ◎ 第9章のミニまとめ
> 1つのAIに全部やらせない。Claude（チャット）は設計者、Claude Code は実装者、GitHub Desktop は本番への扉。それぞれの持ち場を尊重することが、結果として一番早い。


## 第10章：教材としてのサイト、教材としての記事

完成した `/salon/` ページを眺めていて、ふと思いました。

このページ、サロンの参加者のみなさんに**見せられる**のだ、と。

「先生のサイト、AIで作ったんですよ」と言いながら、画面を一緒に見る。「ここが、みなさんが集まっているサロンを紹介しているところです」「ボタンを押すと、自治会の公式ページに飛びますよ」と。

そうやって、サロンで普段話している「AIってこういうものですよ」が、**目の前の具体物として現れる**。

---

私は普段、サロンで「AIと競争しない」という話をします。AIに置き換えられるかもしれないと不安になっている方には、「使う側に回りましょう」と伝えています。

でも、これだけだと**抽象**です。

「使う側に回る」とは具体的にどういうことなのか。それを言葉だけで説明するのは難しい。「実際に使っている人の姿を見せる」のが、一番効きます。

私は教育者として、その**使っている姿**でありたいと思っています。AIで作ったサイトを見せ、AIで作った教材を配り、AIで書いた記事を読んでもらう。「先生、本当に使ってるんだ」と感じてもらうこと。それが、私にとってのAIリテラシー教育の核です。

> 【哲学】
> 「使い方を学ぶこと」と「使う姿を見せること」は、別の教育だ。
> 前者は教室の中で完結する。後者は、自分の活動全体が教材になる。
> サロンで操作方法を教えるだけでなく、サロンを紹介するサイトをAIで作って公開している、という事実そのものが、参加者にとっての教材になる。

そしてこの記事も、その教材の一部です。

サイトを作るプロセスを言葉にし、つまずいたところも、設計判断も、3ツールの役割分担も、全部書いて公開する。これを読んだ方が「あ、こういう風に進めればいいのか」と思えたら、その人は次の一歩を踏み出せる。

私が前回記事で書いた「Claude Design 処女作」を読んで、自分でもサイトを作ってみたくなった方もいるかもしれません。今回の記事を読んで、自分のサイトに地域活動への動線を引いてみたくなった方もいるかもしれません。

そうやって、**使う姿を見せ続ける**こと。それが、yk_memo というブランドで私がやりたいことです。

> ◎ 第10章のミニまとめ
> サイトも記事も教材になる。「使い方を教える」だけでなく「使っている姿を見せる」ことで、AIリテラシー教育は具体になる。

## 終わりに：次は Notes に `tags: salon` を付けにいく

完成した `/salon/` ページの「関連する記事」セクションには、いま「準備中です」と表示されています。

これは仕様どおりで、`tags` に `"salon"` を含む Notes 記事が増えてくると、自動的にここにリストアップされる仕組みになっています。

なので、次の小さな作業は決まっています。

既存のサロン関連 Notes ——salon-qa-generator の話、教材作成の話、NotebookLM の60スライドの話、そして**この記事**——に `tags: ["salon"]` を付けにいくこと。それだけで、`/salon/` ページの「準備中です」が、実際の記事一覧に変わります。

それは、別の日の小さな仕事です。今日は、ここまで。
