## はじめに

**2記事目を「30分で公開」するつもりが、4時間かかって最終的に巻き戻し。その翌朝、私は記事を追加する仕組みそのものを作り変える決断をしました。設計を変えた今日、新しい記事は本当に「.mdファイルを1個置くだけ」で公開できるようになっています。**

私は八王子・片倉台で月次のスマホ・わいわいサロンを運営している、シニア向けAIリテラシー教育者です。yk_memoというブランドで活動しています。前々回(4月26日)にClaude Designでサイトを構築し、前回(4月27日朝)に2記事目を公開しようとして、構文エラーに4時間ハマって最終的に巻き戻した経験を書きました。

この記事は、その「巻き戻した翌朝」から始まる2日間の記録です。読み終えると、次の3つがわかります。

- 非エンジニアが「サイトの設計を変える」決断をどう下したか
- Claude Codeの「OpusとSonnetの使い分け」が、なぜ重要だったか
- プラン使用率を画面下部に常時表示する設定の入れ方

> 【現場レポ】2026年4月28日朝から4月29日朝にかけての、サイト設計変更の体験記です。Astro Content Collectionsへの移行、Opusと Sonnetの使い分け、94%という危険水位で踏みとどまった判断、そしてプラン使用率の常時監視まで、現場で起きたことをそのまま記録しました。

対象読者は、**前2記事を読んでくださった方**、**Claude Codeを使ってみたいけれど「失敗が怖い」と感じている方**、そして**自分のサイトを長く育てていきたい非エンジニアの方**です。

## H2-1：「壊れた家を直す」より「設計図を書き直す」

**前日の朝、サイトに2記事目を追加する作業で、私は構文エラーに4時間ハマりました。最後は git restore で全部巻き戻して、サイトを健全な状態に戻したところで一日を終えました。その夜、寝る前に「明日、もう一度同じ手順で挑戦するか?」と自問したとき、答えは「ノー」でした。**

前日のつまずきは、たまたま運が悪かったからではありませんでした。私が使っていたサイトの構造に、**根本的な問題**があったのです。

具体的には、`src/pages/notes/[slug].astro` という1つのファイルの中に、すべての記事の本文が JSX(JavaScript の拡張記法)として直書きされていました。1記事目を書いた段階で約1,500行。ここに2記事目を追加しようとすると、約3,000行を超えるサイズになります。

そして問題は「サイズ」ではなく「**仕組み**」にありました。Markdown原稿の中に書いた `<li>` や `<section>` のような「HTMLタグの文字」を、Astroがファイルとして読み込むとき、**実際のタグだと誤解する**仕様だったのです。これを Markdown 原稿側で `&lt;li&gt;` のようにエンティティ化すれば回避できますが、原稿を毎回そう書き換える運用は現実的ではない。

> 【哲学】壊れた家を必死で直し続けるより、住みにくい家ならいっそ設計図から書き直したほうがいい。これは月次サロンで「アプリの不具合は、まずアプリの作り直しを検討してください」と教えるのと同じ判断です。今回、その教えを自分自身に向ける番でした。

そこで翌朝、Claude のチャット画面に「**昨日のトラブルは、本当に直すべきなのか?それとも設計を変えるべきか?**」と相談しました。返ってきた答えは、3つの選択肢でした。

| 案 | 概要 | 所要時間 |
|---|---|---|
| 案A | 原稿の `<タグ>` 文字を事前にエンティティ化してから追加 | 30〜45分 |
| 案B | Markdown ファイルを Astro が直接読み込む方式に切り替え | 60〜90分 |
| 案C | Content Collections に移行(Astroの公式パターン) | 90〜120分 |

案Aは応急処置で、来月3記事目を書く時にまた同じ悩みが再発する。案Cは将来見据えた本格設計だけれど、サイトがまだ4記事の段階では「やり過ぎ」かもしれない。**案Bが「今日中の公開」と「将来の楽」を両立する**——その判断で、私は案Bを選びました。

ただし、ゴールも切り直しました。**「今日中に2記事目を公開する」のではなく、「今日は設計変更まで、新記事の追加は明日以降に差し替えてもOK」**と。これが、結果的にこの2日間で一番大きな決断でした。

## H2-2：OpusとSonnet、賢く使い分ける

**設計変更を始める前に、もう1つ大事な気づきがありました。前日トラブった本当の理由は、構文エラーだけではなかったのです。Claude Codeのモデル選択にも、改善の余地がありました。**

前日、私はClaude Codeのモデルを **Opus 4.7**(Anthropic の最上位モデル)に変更していました。「賢いモデルなら、難しい作業もうまくやってくれるだろう」と期待してのことでした。ところが、これがプラン上限到達を加速させていたのです。

整理すると、こういうことでした。

| 観点 | 影響 |
|---|---|
| 同じ作業量で消費するトークン数 | Opus 4.7 と Sonnet 4.6 でほぼ変わらない |
| **プラン上限の消費速度** | **Opus は Sonnet の数倍速い** |
| Claude Codeの内部動作 | 1つの依頼で 8〜10サイクルの推論を回す |

つまり、Claude Codeは「ユーザーから見ると1回の依頼」でも、**内部では何度も推論を繰り返している**。それが Opus だと、1サイクルあたり Sonnet の数倍消費する。前日、4時間ずっと Opus で原因究明と試行錯誤を続けた結果、**プラン上限に2回も到達**したのです。

幸い、Claude Codeには公式の解決策がありました。**`/model opusplan`** という、計画フェーズと実行フェーズで自動的にモデルを切り替えるモードです。

| フェーズ | 使われるモデル | 役割 |
|---|---|---|
| 計画(Plan) | **Opus 4.7** | 深い推論で全体設計を考える |
| 実行(Execute) | **Sonnet 4.6** | 計画に従って機械的にコードを書く |

このモードでClaude Codeを起動すると、**「考えるべき場面」では Opus が動き、「手を動かすだけの場面」では Sonnet が動く**ように、自動で切り替わります。コストは数分の一になり、それでいて品質は十分に保たれる。

> 【哲学】これは、私が前回記事の最後に書いた「悩んだらチャット、手を動かすときはCode」を、**もう一段深めた哲学**でした。同じ Claude Code の中でも、「悩むモデル」と「動くモデル」を分ける。シニアサロンで「画面の操作と頭の整理は別の作業ですよ」と教える話と、まったく同じ構造でした。

設計変更の作業を始める前に、Claude Codeの入力欄でこのコマンドを打ちました。

```
/model opusplan
```

たった1行のコマンドですが、これが今回の作業を**最後まで走り切らせる土台**になりました。

## H2-3：3つのフェーズに分けて、確実に進む

**「案Bで設計変更する」「Opus と Sonnet を使い分ける」「ゴールは設計変更まで」——この3つを決めたところで、ようやく実装に入りました。Claude Codeへの依頼の出し方にも、前日からの学びを反映させました。**

前日の失敗の1つは、Claude Codeに「全体ゴール」を渡して任せたら、**勝手に次のフェーズへ進んでしまう**ことでした。これを防ぐため、今回は作業を**3つのフェーズに明確に分ける**やり方にしました。

| フェーズ | 内容 | 所要時間の目安 |
|---|---|---|
| Phase 0 | 計画提示(まだ実装しない) | 5〜10分 |
| Phase 1 | Content Collectionsの設定 + 既存4記事を .md に移行 | 25〜35分 |
| Phase 2 | 3つのテンプレートファイルを書き換え | 15〜20分 |
| Phase 3 | 検証(`npx astro check`、`npx astro build`) | 5〜10分 |

そしてClaude Codeに送るプロンプトには、こう明記しました。

> 「Phase 0(計画提示)だけを実行してください。実装には絶対に着手しないでください。」

これは前回記事の哲学**「実行前に内容が分かる安心感」**を、もう一段強く効かせる工夫です。**「次のフェーズに進まない」を毎回プロンプトに書く**だけで、独走が大幅に減りました。

Phase 0でClaude Codeが提示してきた計画は、想像以上に質が高いものでした。Astro v6 の Content Layer API という最新の仕様を踏まえ、`src/content/config.ts`(後で位置を修正することになる)で記事のスキーマを定義する案。`status: published / draft` というフィールドで「本文あり/準備中」を区別する案。`<table>` のような複雑な要素は HTML のまま残す判断。

最後にClaude Codeはこう聞いてきました。

> 「現状 `salon-ai-hajimete`(本文未着手の記事)がトップページに表示されていますが、移行後は『本文ありの記事のみ』をトップに出す動作に変わります。問題があればお知らせください。」

**機械が、人間に判断を委ねた瞬間**でした。私は「計画通りでOK」と返し、Phase 1 が始まりました。

## H2-4：プラン使用量94%、ストップする勇気

**Phase 1 が完了して、Phase 2 に入ろうとしたとき、画面に「プラン使用量 94%」の表示が出ました。前日と同じ警告です。ここで私は、ある決断をしました。**

Phase 1 では、`src/content/notes/` フォルダを作り、既存4記事の本文を Markdown ファイルに分解する作業をしました。約1,500行の JSX が、`.md` ファイル4つに分解されました。Claude Codeは丁寧に変換し、表(`<table>`)はHTMLのまま、その他はMarkdown記法に変換する判断を見せました。

そして「Phase 2 に進みますか?」というところで、94% という表示。

| 残量 | 状況 | 大規模作業を進めるべきか |
|---|---|---|
| 80%以上 | 余裕 | ✅ 進める |
| 50% | 慎重に | ✅ 進めるが要監視 |
| 30% | 警戒水域 | ⚠️ 短い作業のみ |
| 20%以下 | 危険 | ❌ 停止推奨 |
| **94%(つまり残り6%)** | **完全危険** | **❌ ストップ一択** |

前日も、私は同じ場面で**「もう少し進めれば終わるかも」**と賭けに出て、結果的に途中でプロセスが止まり、ファイルが半端な状態で残ってしまいました。今回はその経験があったので、迷いませんでした。

Claude Codeに「ここで一旦停止してください」と伝え、Phase 2は**プランがリセットされた後**に再開することにしました。

> 【哲学】「あとちょっとで終わる」という判断は、たいてい当たりません。私は月次サロンで「**スマホの容量が90%を超えたら、まず使わないアプリを消してから写真を撮ってください**」と教えています。今日、自分も同じ判断をしました。**残量が少ないときは、新しい大きな作業を始めない**。これは生活の中で、何度も繰り返し練習している判断です。

リセット後、Phase 2 はスムーズに完了しました。`[slug].astro` が**1,445行から334行に縮小**。1,111行ぶんの本文JSXブロックが、`.md` ファイル4つに分散され、テンプレートからは消えました。

ところが、ここで小さな伏兵がいました。**Astro v6 では Content Collectionsの設定ファイルの置き場所が変わっていた**のです。

| バージョン | 設定ファイルの位置 |
|---|---|
| v3〜v4 | `src/content/config.ts` |
| **v5以降** | **`src/content.config.ts`**(新方式) |

Phase 0 の計画段階では古い情報のままでした。`mv` コマンド1行で位置を直して、サーバー(`npm run dev`)を再起動したら、エラーは消え、サイトは完全に動きました。設計変更、完了です。

## H2-6：GitHub Desktop で「main にマージする」までの3ステップ

**ローカルで動作確認できたら、最後の関門は GitHub Desktop での操作でした。前日の作業で「commit と push の違い」「Fetch origin との違い」が頭にスッと入っていたので、ここはスムーズに進みました。**

GitHub Desktop には、混乱しやすいボタンが3つあります。**この3つの違いを理解すれば、もう迷子になりません**。

| ボタン名 | 動作 | いつ使う |
|---|---|---|
| **Fetch origin** | GitHubから最新を取得・確認のみ | 普段の確認 |
| **Commit to ...** | ローカル履歴に「変更を記録」 | 編集が一区切りついたとき |
| **Push origin** | ローカルのcommitをGitHubに送信 | 本番に反映したいとき |

私が今回辿った流れは、こうです。

```
[1] 新記事の .md ファイルをローカルに置く
       ↓
[2] GitHub Desktop が「変更あり」を検知
       ↓
[3] Commit to feature/content-collections で記録
       ↓
[4] Push origin で GitHub に送信
       ↓
[5] main ブランチに切り替え
       ↓
[6] Branch メニューから「Merge into Current Branch...」
       ↓
[7] 「feature/content-collections」を選んでマージ
       ↓
[8] 「Push origin ↑ 2」で main を GitHub へ
       ↓
[9] Vercel が自動デプロイ → 本番反映
       ↓
[完了] yk-memo.vercel.app/ で新記事が公開
```

特に注意したのは、**ブランチを2つ使い分ける運用**でした。

| ブランチ | 役割 |
|---|---|
| `main` | **本番に反映される枝**(Vercel が自動デプロイの対象として見ている) |
| `feature/content-collections` | **作業中の枝**(失敗してもmainには影響しない) |

設計変更のような大きな作業は、新しいブランチを切ってから作業し、動作確認できたら main にマージする。これが Git の世界の作法です。**最初は1ブランチだけで動かして、慣れてからブランチを増やす**くらいで十分かもしれません。

> 【哲学】これは、月次サロンで「**料理を作る前に、まず別の鍋にお湯を沸かしておくと、最後に台所が綺麗です**」と教えるのと似ています。**作業のための「別の場所」を最初に用意しておく**と、本番に影響を与えずに試行錯誤できる。Git のブランチも同じ発想です。

## H2-7：プラン使用量を「画面下部に常時表示」する

**今回の体験を踏まえて、もう1つ仕組みを入れました。Claude Code のプラン使用量を、画面下部に常時表示する設定です。これがあれば、94%まで気づかずに突き進む事態は、もう起きません。**

設定するのは「Status Line(ステータスライン)」というClaude Code公式の機能です。`pipx`(Pythonアプリの安全なインストーラ)で1つパッケージを入れると、画面下部にプラン使用率が常時表示されるようになります。

ターミナルで打つコマンドは、たった1つでした。

```bash
pipx install claude-statusbar
```

インストールが終わると、Claude Code の設定ファイル `~/.claude/settings.json` に、自動でこのような設定が追加されます(設定が入らない場合は手動で追記します)。

```json
{
  "model": "opusplan",
  "statusLine": {
    "type": "command",
    "command": "/Users/(ユーザー名)/.local/bin/cs"
  }
}
```

Claude Code を起動すると、画面の一番下に、こんな1行が表示されるようになります。

```
5h[█░░░░░░░░░] 5% ⏰4h45m | 7d[███░░░░░░░] 33% ⏰3d05h | Sonnet 4.6
```

それぞれの意味はこうです。

| 部分 | 意味 |
|---|---|
| `5h[█░░░░░░░░░] 5%` | 5時間ローリング枠の使用率 |
| `⏰4h45m` | 5時間枠のリセットまでの時間 |
| `7d[███░░░░░░░] 33%` | 7日枠の使用率 |
| `⏰3d05h` | 7日枠のリセットまでの時間 |
| `Sonnet 4.6` | 現在使われているモデル |

そしてこの数字は、使用率に応じて**色が変わります**。

| 使用率 | 色 | 行動指針 |
|---|---|---|
| 0〜30% | 🟢 緑 | 普通に作業 |
| 30〜70% | 🟡 黄 | 中規模作業まで、大きな計画は避ける |
| 70%以上 | 🔴 赤 | 軽い作業のみ。次の自然な区切りで止める |
| 90%以上 | 🔴 赤(濃) | **賭けに出ない、即停止** |

> 【哲学】これは、前回記事の哲学**「困ったら手を止める」**を、**システムに任せた**仕組みです。私が「画面を見つめる3秒」を意識しなくても、画面が私に「そろそろ止めたほうがいい」と知らせてくれる。**人間の意志に頼らず、データが背中を押してくれる**——これは、シニアサロンで「アラームをかけておくと、忘れない」と教えるのと同じ発想です。

## H2-8：この2日間で、本当に学んだこと

**この記事で書ききれない学びも、たくさんありました。最後にいくつか、特に大きかったことを書き残しておきます。**

### 学び1:**「動くもの」を最優先にする**

前日、私が4時間かけてもエラーが消えなかった時、Claude Code は5段階の仮説検証を経て原因を絞り込んでくれました。それでも完全には直らなかった。**そのときの判断**が、今回の鍵でした。

私が選んだのは「**さらに直し続ける**」ではなく「**いったん git restore で、サイトを動く状態に戻す**」ことでした。Vercel で公開しているサイトは、訪問者が見にくる場所です。**壊れたまま放置するより、健全な状態に戻すほうが優先**でした。

### 学び2:**「失敗からの学び」をシステムに組み込む**

94%でストップした判断、意識して止まれたのは、前日にすでに同じ場面で失敗していたからでした。そして今日、その経験を「**プラン使用量の常時表示**」というシステムにまで昇華させました。

| 段階 | 状態 |
|---|---|
| 初体験 | 気づいたら94%、どうしようもない |
| 2回目 | 「あ、94%だ」と気づける |
| 3回目以降 | システムが自動で警告してくれる |

**経験を、データに変える**——これが今回の2日間の核心でした。

### 学び3:**「お任せ」は、たいてい良い結果を生まない**

Claude Code は強力ですが、**「全部やっておいて」と任せるのは危険**です。今回も、Claude Codeが「次のフェーズに勝手に進む」場面が何度かありました。プロンプトの中で**「Phase 2 には絶対に進まないでください」と明記する**ことで、独走を確実に防げました。

これは、月次サロンで参加者に「**AIに『よろしく』と伝えるだけでは、欲しいものは手に入りません**」と教えていることと、完全に同じでした。**「何をするか・何をしないか」を、こちら側がはっきり伝える**。それが、AI時代の「お願いの作法」です。

### 学び4:**「未来の自分のために、少しの時間を使う」**

設計変更には、結果的に**約4時間**かかりました。たった1記事を公開するためだけなら、過剰な投資にも見えます。でも、これから書く3記事目、4記事目、5記事目……と続けていくと、**「.mdファイルを1個置くだけ」**で済む差は、確実に積み上がっていきます。

**今日、自分のために少しの手間をかけておくと、明日以降の自分が楽になる**——これは、私が月次サロンでずっと参加者の方々に伝えてきたメッセージそのものでした。AIとの付き合い方も、シニアの皆さんへのスマホ教育も、根っこは同じです。

## おわりに

**2日間かけて、私はサイトの「設計図」を書き直しました。仕組みを作り変えたあとの最初の記事公開は、本当に30分で終わりました。これからは、原稿を書き終えたら、`.md`ファイルを1個置くだけで、サイトに新記事が増えていきます。**

サイト構築の翌朝に2記事目を公開して4時間ハマった話、ハマった夜に巻き戻して翌朝設計を変えた話、そして翌朝にスムーズに2記事目が公開できた話。3記事連続でお読みくださった方には、**この一連のストーリーが、ひとつの「学びの旅路」**として伝わったらうれしいです。

そして何より、**「失敗を、未来の自分への贈り物に変える」**という選択肢が、AIと付き合う日常の中に確かに存在することを、皆さんと共有できたら幸いです。

来月のスマホ・わいわいサロンでは、この2日間の話を、参加者の皆さんに「シニアでもできる失敗との付き合い方」として伝えるつもりです。AIとの付き合い方も、スマホとの付き合い方も、生活との付き合い方も——根っこのところで、たぶん同じことを練習しているのだと思います。
