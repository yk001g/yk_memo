# Claude Code「Dynamic Workflows」完全ガイド｜数百体のAIが自律的に検証し合う仕組みと非エンジニア活用法

> [!info] この記事について
> 本記事はAnthropic公式ブログ・公式ドキュメント・複数の技術メディアの一次情報をもとに構成しています。主要な事実には出典を明記しました。Dynamic Workflowsは2026年6月時点で「リサーチプレビュー」段階のため、トークン消費量や起動UIは今後変更される可能性があります。

---

## Dynamic Workflowsとは何ですか？

**Dynamic Workflowsとは、Claude Codeがタスクに応じた作業計画をその場で自動生成し、数十〜数百体のサブエージェントを並列実行させ、結果を相互検証してから最終的な答えだけを返す機能です。2026年5月28日にClaude Opus 4.8と同時公開されました。一言でいえば「Claudeが現場監督になり、AIチームに仕事を発注する」仕組みです。**

従来のClaude Codeは、1体のエージェントがファイルを順番に読み、コンテキスト（作業机）に情報を積み上げながら処理していました。しかしこの方式には限界があります。サービス全体のバグ調査や数百ファイルに及ぶ移行作業のような大規模タスクでは、机が埋まり、途中で「すでに何を確認したか」を見失ってしまうのです。

Dynamic Workflowsはこの問題を解決します。利用者がやることは「タスクを言葉で説明する」だけ。あとはClaudeが、どう分割するか・何体のサブエージェントを立てるか・どう検証するかをすべて自分で決めて実行します。

Anthropicは公式ブログでこの機能を、複雑な仕事を端から端まで自律的にこなすものと位置づけています。

> 【補足】チャエン氏（@masahirochaen）はXで「Claudeの中の人いわく『skills以来、最大のアップデート』」と紹介しています。これは内部の評価を伝聞として紹介したもので、Anthropic公式の文言ではありませんが、機能のインパクトの大きさを示すエピソードとして注目されています。

## なぜ従来の「1体のAI」では足りなかったのですか？

**1体のAIで長時間タスクを処理すると、コンテキスト（作業机）が肥大化し、途中で確認漏れや自己評価の甘さが生じます。Dynamic Workflowsは作業を複数のAIに分散し、中間結果を会話の外（スクリプト）で保持することで、この限界を構造的に突破します。**

技術メディアのclaudefa.stは、この問題の構造を具体的に説明しています。単一のエージェントはファイルを順番に読み、コンテキストを構築し、やがて上限に達する。それまでに確認済みの内容を見失うか、会話を圧縮して以前のファイルの発見事項を忘れてしまうのです。

これまでの回避策は「サブエージェントを手動で立てる」ことでした。しかしその場合、何体のサブエージェントを立てるか、どう作業を分割するか、どう結果を統合するかを事前に自分で把握しておく必要があったのです。初めて触るコードベースのバグ調査では、そもそもその知識がありません。

Dynamic Workflowsは、この「事前に分割設計を知っていなければならない」というハードルそのものを取り除きました。

### 1体のAIが長時間タスクで陥りやすい3つの問題

チャエン氏のスレッドでは、この限界が「1人の職人が全部を自分の机で処理する」状態として、わかりやすく3つに整理されています。

| 問題 | 内容 |
|---|---|
| ① 怠ける | 長時間稼働で処理が雑になる |
| ② 自分に甘い | 自己評価が甘くなり、不十分な結果でも「完成」と判断する |
| ③ 目的がブレる | 当初の目的から徐々にずれていく |

Dynamic Workflowsは、作業役とは別に「検査専門」のエージェントを立てることで、特に②の「自分に甘い」問題を構造的に防ぎます。これは次の章で詳しく見る「敵対的検証」の核心です。

## Dynamic Workflowsはどう動くのですか？（3つの核心メカニズム）

**Dynamic Workflowsの核心は「並列ファンアウト」「敵対的検証」「収束するまでの反復」の3つです。Claudeがタスクを分割して数百体のサブエージェントに並列発注し、別のエージェントがその結果に反論を試み、答えが収束するまで反復します。**

Anthropic公式ブログは仕組みをこう説明しています。ワークフローが起動すると、Claudeはプロンプトに基づいて動的に計画を立て、サブタスクに分解し、並列実行されるサブエージェントに作業を展開する。結果は統合される前にチェックされる。さらにエージェントが独立した角度から問題に取り組み、別のエージェントが見つけたことに反証を試み、答えが収束するまで反復し続けるのが特徴です。

### ① 並列ファンアウト（数十〜数百体規模）

最大の進化はスケールです。単一セッション内で数十から数百の並列サブエージェントを実行することができます。公式ドキュメントによれば、**1回のワークフローで起動できるサブエージェントは最大1,000体、同時に並列実行されるのは最大16体**という上限が設けられています。「数百体」という表現は、この“延べ起動数”のスケール感を指しています。

これがどれほど大きな変化かというと、人間が手で組むマルチエージェント構成は、たいてい4〜5体が限界です。なぜなら、それが人間のワーキングメモリで管理できる上限だから。しかしClaude自身がオーケストレーション（指揮）を担う場合、その制限がなくなります。

### ② 敵対的検証（反証役を立てる）

これがDynamic Workflowsを「ただの並列実行」と分ける決定的な違いです。

サブエージェントは発見を報告するだけではありません。**別のサブエージェントが、その発見に反論する役割を担います。** あるサブエージェントが「この関数には競合状態（レースコンディション）がある」と主張したら、別のサブエージェントの仕事は「それを反証すること」。反証をくぐり抜けた主張だけが、利用者の手元に届きます。

> 【現場の視点】これは業務委託で「作業した本人に検収させない」という組織論と同じ原則です。自分で書いたコードを自分でレビューすると見落としが生じますが、第三者の「粗探し役」を立てると品質が跳ね上がる。Dynamic Workflowsはこれをエージェントの構造として組み込んだわけです。

### ③ 収束するまでの反復

ワークフローは「答えが変わらなくなるまで」走り続けます。あらかじめステップ数が決まったパイプラインとは違い、**サブエージェントの数も反復回数も、実際の作業が必要とする量に応じてリアルタイムで決まります。**

さらに公式ブログによれば、処理の進捗は保存されるため、中断されたジョブは最初からやり直すのではなく、中断したところから再開するとのこと。数時間〜数日に及ぶ長時間タスクでも安心して任せられる設計です。

## どうやって起動しますか？（3つの方法）

**Dynamic Workflowsの起動方法は主に3つあります。①「ワークフローを作って」と自然言語で頼む、②effortメニューで`ultracode`設定をオンにする、③`/deep-research`などの組み込みワークフローを使う、です。初めてなら①か③が簡単です。**

### 方法①：自然言語で頼む（最もシンプル）

Claudeに直接、やってほしいことを伝えるだけです。

```
> 認証モジュールの競合状態を、全サービスエンドポイントにわたって監査するワークフローを作って。
```

Claudeがこの依頼を「Dynamic Workflowsのパターンに合う」と判断し、分割計画を立て、これから何を実行するかを表示します。利用者が確認（承認）すると、サブエージェントが動き出します。

### 方法②：`ultracode`をオンにする

Claude Codeのeffort（努力度）メニューで`ultracode`を選ぶ方法です。これはeffortレベルを最大級の`xhigh`に設定し、**「ワークフローを作って」と明示的に言わなくても、Claudeが自分でワークフローを使うべきタイミングを判断してくれます。**

ただしこの設定は現在のセッションのみ有効で、新しいセッションを始めるとリセットされます。

### 方法③：`/deep-research`（組み込みワークフロー）

特定のテーマについて、複数のAIが相互にファクトチェックし、引用付きで回答してくれる組み込みワークフローです。チャエン氏も「迷ったら④（/deep-research）から試すのがおすすめ」と紹介しています。

> 【現場の判断】初めて触る人には方法③が一番おすすめです。スコープ（範囲）が明確で、出力も「引用付きの調査レポート」という形でわかりやすいため、トークン消費の感覚をつかむ練習に向いています。

### 重要：Auto Mode（自動モード）と必ず併用する

Anthropic公式はDynamic Workflowsを使うときはauto modeをオンにすることを推奨しています。

理由はシンプルです。数百体のサブエージェントを動かすワークフローが、サブエージェントの操作のたびに許可確認で止まっていたら、まったく並列処理になりません。承認ボタンを押し続けるだけでセッションが終わってしまいます。Auto Modeは、危険な操作をAI分類器がブロックしつつ、サブエージェントを止めずに動かし続けます。

### 初回は必ず確認画面が出る

安全装置として、ワークフローが初めて起動するとき、Claude Codeは何が実行されようとしているかを表示し、確認を求める仕組みになっています。意図せず200体のサブエージェントを起動してしまう事故を防ぐためです。

## どのプランで使えますか？利用環境まとめ

**Dynamic Workflowsはすべての有料プラン（Pro / Max / Team / Enterprise）で利用できます。ただしデフォルトの状態がプランごとに異なります。MaxとTeamは初めからオン、Proは`/config`で有効化、Enterpriseは管理者の許可が必要です。**

| 項目 | 内容 |
|---|---|
| ステータス | リサーチプレビュー |
| 対象プラン | Pro / Max / Team / Enterprise（全有料プラン） |
| デフォルト状態 | Max・Teamはオン／Proは`/config`で有効化／Enterpriseは管理者が許可するまでオフ |
| 対応環境 | Claude Code CLI、デスクトップアプリ、VS Code拡張、Claude API、Amazon Bedrock、Vertex AI、Microsoft Foundry |
| リリース日 | 2026年5月28日 |
| 管理者制御 | 組織管理者がワークフローを無効化可能 |

注目すべきは、リリース初日からVS Code・Bedrock・Vertex・Foundryに対応している点です。claudefa.stはこれはAnthropicがDynamic WorkflowsをCLI限定の実験ではなく、中核インフラとして扱っているサインだと指摘しています。

> 【補足】チャエン氏のスレッドでは「Pro含む全プランで使える」「v2.1.154以上が必要、Proは手動で有効化」と紹介されていました。バージョン番号は記事公開時点の情報のため、ご自身の環境でClaude Codeを最新版に更新してから`/config`を確認するのが確実です。

## 実際にどんなことができるのですか？（公式事例）

**Anthropicは公式に、コードベース全体のバグ調査・セキュリティ監査・大規模移行・「二重チェックが必要な重要作業」を主な用途として挙げています。象徴的な実例が、Bun（JavaScriptランタイム）の約100万行に及ぶZig→Rust移植です。**

### 象徴的事例：Bunの約100万行コード移植

最も極端な事例が、Bunの全面書き換えです。Bunの作者Jarred Sumner氏が、Dynamic Workflowsを使ってBunをZigからRustに移植しました。

| 指標 | 数値 |
|---|---|
| 生成されたRustコード | 約96万〜100万行（報道により75万行とも。The Registerは「100万行超」） |
| 既存テスト通過率 | 99.8%（Linux x64 glibc） |
| 期間 | 約6日（最も広く報じられた数字。コミット→マージの起点の取り方で出典に幅あり） |

公式ブログによれば、この移植は段階的に行われました。あるワークフローがZigコードベースの全構造体フィールドに対して正しいRustのライフタイムをマッピングし、次のワークフローが各.zigファイルと挙動が同一の.rsファイルを書いた。数百体のエージェントが並列で作業し、各ファイルに2名のレビュアーがついたとのこと。その後、修正ループがビルドとテストをクリーンになるまで回しました。

Anthropicはこれを通常は四半期単位で計画する作業が、数日で終わると表現しています。

> 【注意点・賛否両論】チャエン氏も指摘するとおり、この移植は2026年6月時点で「まだリリースビルドに載っていないPoC（概念実証）」段階です。批判の核心は**unsafeブロックの数**で、生成されたRustコードには**13,365個のunsafeブロック**が含まれていました（比較対象のRustプロジェクトuvはわずか73個）。コミュニティからは「vibecoded disaster（雰囲気コーディングの惨事）」との反発も出ました。さらに「テストの一部がZig版から忠実に移植されず、Rust版向けに改変された疑いがあり、99.8%という通過率は見かけほど安心できない」という鋭い指摘もあります（[byteiota](https://byteiota.com/bun-rust-rewrite-merged-the-13000-unsafe-block-problem/)、[The Register](https://www.theregister.com/devops/2026/05/14/anthropics-bun-rust-rewrite-merged-at-speed-of-ai/5240381)）。スケール感は本物ですが、品質保証は別問題、という冷静な視点が大切です。

### 企業の実例：Klarnaの「死んだコード」発見

スウェーデンの金融企業Klarnaのシニアエンジニアリングマネージャー、Alessio Vallero氏は次のように評価しています。Dynamic Workflowsは大規模コードベースの調査・レビュータスクで特に価値があった。従来の静的解析が見逃していたデッドコード（使われていないコード）を特定し、クリーンアップの機会を浮かび上がらせるのに強い結果が出ている。

ポイントは「従来の静的解析が見逃していた」という部分です。静的解析ツールは構文（シンタックス）を見るだけですが、Dynamic Workflowsは「そのコードが本番環境のパスで実際に到達可能か」まで推論できます。

### 企業の実例：CyberAgentの「ちょうど中間」評価

CyberAgentのリードシステムエンジニア、Ken Takao氏のコメントも、この機能の立ち位置を的確に表しています。Dynamic Workflowsは、単一のサブエージェントを起動することと、本格的なエージェントチームを構築することの間のギャップを埋める。計画から実装までスムーズに流れるので、可視性を失わずに長時間の実行を信頼できる。

## 非エンジニアでも使えますか？（むしろ本命）

**使えます。むしろ開発者本人が「非エンジニアの用途に一番ワクワクしている」と語っています。事業計画の多角的批評、大量書類のランク付け、文章のファクトチェックなど、入力が明確で完了判定ができる業務全般に有効です。**

チャエン氏のスレッドで紹介されている非エンジニア向けの活用例は、tetumemoの読者層にとっても示唆的です。

- **事業計画を投資家・顧客・競合の3視点で批評する** — それぞれの立場のエージェントを立て、敵対的に検証
- **履歴書80枚をランク付けし、上位10名を再チェックする** — 大量生成→絞り込みの型
- **ブログ原稿の技術的主張を全部ファクトチェックする** — 各主張を独立したエージェントが検証
- **Slackの#incidentsチャンネル半年分から根本原因を発掘する** — 大量ログの横断分析
- **CLIツールの名前をトーナメント形式で決める** — 候補を比較して勝者を決定

> 【現場の判断】この5つに共通するのは「入力が明確」「出力形式が決まっている」「完了判定ができる」という3条件です。逆にいえば、ゴールが曖昧なタスク（「いい感じにして」など）には向きません。非エンジニアがDynamic Workflowsを活かす鍵は、コードを書く力ではなく「自分の業務を明確なゴールで定義する力」にあります。

## Claudeが使う6つのワークフローの「型」

**Dynamic Workflowsには代表的な6つの「型」があります。分類して振り分け／分割→並列→統合／敵対的検証／大量生成→絞り込み／トーナメント／終わるまでループ、の6つです。「敵対的に検証して」「トーナメントで選んで」と具体的に指定すると精度が上がります。**

| 型 | 動き | 向いているタスク例 |
|---|---|---|
| 分類して振り分け | タスクをカテゴリ分けして担当を割り振る | 大量の問い合わせメールの仕分け |
| 分割→並列→統合 | 大きな作業を分けて並列処理し統合 | 数百ファイルの一括変換 |
| **敵対的検証**（反証役を立てる） | 発見に対し別エージェントが反論 | セキュリティ監査・重要な意思決定 |
| 大量生成→絞り込み | 候補を量産してから選抜 | アイデア出し・履歴書スクリーニング |
| トーナメント | 比較対戦で勝者を決定 | ネーミング・コピー案の選定 |
| 終わるまでループ | 完了条件を満たすまで反復 | テストが全部通るまでの修正 |

このうちチャエン氏が「一番効く」と強調しているのが**敵対的検証**です。前述のとおり、これがDynamic Workflowsの品質を支える中核メカニズムだからです。

## トークン消費はどのくらいですか？（最重要の注意点）

**Dynamic Workflowsは通常のClaude Codeセッションより「桁違いに」トークンを消費します。Anthropic公式も明確に警告しています。対策は「スコープを絞る」「小さく試す」「上限を指定する」の3つです。**

これは本機能を使ううえで最も重要な注意点です。Anthropic公式ブログはDynamic Workflowsは通常のClaude Codeセッションよりも大幅に多くのトークンを消費する可能性があるため、まず範囲を絞ったタスクで使用感をつかむことを推奨すると明記しています。

特にProプランでは注意が必要です。claudefa.stはワークフローは通常セッションより大幅に多くのトークンを消費するため、1回の大きな実行で上限に一気に近づく可能性がある。スコープを絞って始めることと助言しています。

### トークン消費を抑える3つのコツ

1. **スコープを絞る** — 「全コードベース」ではなく「authフォルダだけ」のように範囲を限定する
2. **小さく試す** — 最初の数回は本番ではなく、感覚をつかむための実験と割り切る
3. **上限を指定する** — プロンプトに「use 10k tokens」のように上限を明示する

claudefa.stが推奨する「キャリブレーション（調整）用」の初回プロンプト例も参考になります。

```
claude --permission-mode auto
> auth/middleware/ フォルダだけを対象に競合状態を監査するワークフローを作って。変更は加えず、発見事項だけ報告して。
```

範囲が十分に狭いのでコストが抑えられ、かつ「ワークフローがどうタスクを分解し、何体のサブエージェントを立てるか」を観察できます。これが大きな作業に進むための基準点になります。

……と、ここまでが「教科書どおりの説明」です。ところが筆者が実際にこの「キャリブレーション実行」をやってみたところ、教科書が崩れました。次の章はその実録です。

---

## 【実体験】「5件だけ」のはずが99体・82万トークン・3時間に

**この記事を書くにあたり、筆者は実際にDynamic Workflowsの`/deep-research`を回しました。テーマは「Dynamic Workflowsのトークン消費批判」——つまりDynamic Workflowsで、Dynamic Workflows自身の弱点を調べたわけです。結論から言うと、「出典5件程度」とスコープを絞ったはずの安全な実行が、99体のサブエージェント・約82万トークン・3時間7分を消費し、最後はレート制限に達して検証フェーズが自滅しました。**

前章で紹介した「まずは範囲を絞ったキャリブレーション実行から」という公式アドバイスを、筆者は忠実に守りました。プロンプトにも「英語圏の技術ブログとHacker Newsを中心に、出典5件程度で」と明示的に上限を書いています。それでも、結果はこうなりました。

| 観察ポイント | 実測値 |
|---|---|
| スコープ指定 | 「出典5件程度」と明示 |
| 実際に立ったサブエージェント数 | **99体** |
| トークン消費 | **約819,800トークン** |
| 所要時間 | **3時間7分23秒** |
| 結末 | 検証フェーズ中に**レート制限に到達**、検証エージェント多数が失敗 |
| 実行モデル | Sonnet 4.6（Opusではなかった） |

> 【現場の視点】これは笑ってしまう体験でした。「Dynamic Workflowsはトークンを食う」という"批判"を調べるために回したワークフローが、**まさにそのトークン消費の激しさで途中で力尽きた**のです。事前に他メディアで読んでいた「62体立ち上げて5時間枠を18分で使い切った」という他人の不満を、筆者は身をもって追体験してしまいました。「スコープを絞れば安全」という説明は、少なくとも`/deep-research`に関しては鵜呑みにしないほうがいい——これが一番の学びです。

### 驚いた点：「5」と書いても「5」では止まらない

最大の誤算は、**出力する出典を5件に絞っても、その5件にたどり着くための裏方が99体動く**ことでした。Dynamic Workflowsの「答えが収束するまで反復する」設計は、裏を返せば「利用者が指定するのは"成果物の量"であって"作業量"ではない」ということです。作業量はClaudeが決める。ここを理解せずに回すと、請求書（トークン）で驚くことになります。

### 期待外れだった点：放置時間とモデル

3時間という所要時間も想定外でした。「数分で感覚をつかむ」つもりが、実態は半日仕事に近い。さらにステータスバーを見ると、検証はOpusではなく**Sonnet 4.6**で回っていました。重い並列処理はコスト効率のためか軽量モデルに振られるようで、「Opus 4.8の高度な推論で検証される」というイメージとは少しギャップがあります。

> 💬 **読者のあなたへ**：この感想は筆者の一例です。あなたが実際に回したときの数字（体数・時間・消費量）は環境やプランで変わります。鵜呑みにせず、ご自身の小さな1回で「相場観」をつかんでから本番に進んでください。

### 収穫：敵対的検証が「本当に効いていた」

ただし、出力の中身には収穫もありました。`/deep-research`は**敵対的検証を3票方式で実施**し、筆者が事前に他メディアで見つけていた刺激的な数字——「1セッション$8,000〜$15,000」「18分で5時間枠を枯渇」「62並列」といった主張を、**「検証を通過しなかった＝確定事実として提示できない」と自ら却下**しました。最終的に3票すべてを通過した確定主張は、たった1つ:

> 「Dynamic Workflowsは通常のClaude Codeセッションよりも大幅に多くのトークンを消費する可能性があり、Anthropic自身が公式にこれを認めている」（[InfoQ](https://www.infoq.com/news/2026/06/dynamic-workflows-claude-code/)、[MindStudio](https://www.mindstudio.ai/blog/how-to-control-token-costs-claude-code-dynamic-workflows)、[Hacker News討論](https://news.ycombinator.com/item?id=48311705)）

これは本記事の第3章で説明した「敵対的検証」が、絵に描いた餅ではなく**実際に甘い主張を弾いていた**証拠です。センセーショナルな数字ほど検証で落ちる——この厳しさこそ、単なる並列検索とDynamic Workflowsを分ける核心でした。一方で、出典URLの捏造（ハルシネーション）は筆者が確認した範囲では起きておらず、引用の信頼性という点では合格でした。

### この実体験から言える3つの教訓

1. **「成果物の量」は指定できても「作業量」は指定できない** — 5件指定でも裏で99体動く。トークンは作業量に比例する
2. **「キャリブレーション=安全」ではない** — 公式の言う小さな実行ですら、Proのセッション枠を一気に削りうる。本当に試すなら使用量に余裕のある時間帯を選ぶ
3. **敵対的検証は本物** — 刺激的な主張ほど落ちる。出力を鵜呑みにせず「何が確定で何が未確定か」を区別して提示してくれる

## 似た機能との違いは？（Auto Mode・Agent Teams・Scheduled Tasksとの比較）

**Dynamic Workflowsは「1つのタスクをどう分割し、何体に展開するか」を決める機能です。許可を自動承認するAuto Mode、役割を事前定義するAgent Teams、実行頻度を決めるScheduled Tasksとは、決定する軸がそれぞれ異なります。組み合わせて使うこともできます。**

| 機能 | 何を決めるか | 向いている場面 |
|---|---|---|
| Auto Mode | 各操作を確認なしで承認するか | 許可確認で流れが途切れる長時間セッション |
| Agent Teams | 役割を固定した専門家チームの連携 | 役割を事前に定義できる領域横断作業 |
| Scheduled Tasks / Routines | いつ・どのくらいの頻度で再実行するか | 定期実行（夜間チェック、週次レポート） |
| **Dynamic Workflows** | 1タスクをどう分割し何体に展開するか | 検証が必要な一発勝負の重要作業 |

この違いを理解すると、組み合わせの設計も見えてきます。たとえば「毎週日曜の夜にDynamic Workflowsの監査を実行するRoutine」は、claudefa.stも妥当なアーキテクチャとして挙げる合理的な構成です。

### いつ使うべきで、いつ避けるべきか

**使うべき場面：**
- コードベース全体の監査（セキュリティ・デッドコード・パフォーマンス）で網羅性が重要なとき
- 数百〜数千ファイルに及ぶ移行を、1つ1つ検証しながら進めたいとき
- 計画を多角的にストレステストしてから着手したいとき
- 不慣れな領域で、まだ作業の分割方法がわからないとき

**避けるべき場面：**
- 1体のエージェントで1回で終わる小さなタスク（トークンコストが見合わない）
- すでに役割分担が明確なとき（Agent Teamsのほうが制御しやすい）
- そのセッションでコストを抑えたいとき
- 毎回まったく同じ計画で実行したいとき（ワークフローは実行時に分割を決めるため）

## オーケストレーションが「人の仕事」から「モデルの仕事」へ

**Dynamic Workflowsが示す本質的な変化は、作業の指揮（オーケストレーション）が開発者の仕事からモデルの判断に移ったことです。利用者の役割は「指揮の設計」から「成功条件・制約・信頼境界の定義」へと一段上がります。**

claudefa.stはこの変化をこう総括しています。以前は、オーケストレーションのロジックをスラッシュコマンドやプロンプトテンプレート、サブエージェントファイルに書いていた。今は、依頼を書けばClaudeがオーケストレーションを書く。

つまり利用者の仕事はもはやオーケストレーションを書くことではない。成功基準、制約、信頼境界を書くこと。オーケストレーションはそれに従うのです。

> 【現場の視点】これは先日話題になった`/goal`コマンドの「業務を明確な完了条件で定義できる人が有利になる」という主張と完全に一致します。AIの性能が上がるほど、勝負どころは「何をしてほしいかを正確に言語化する力」に移っていく。tetumemoが一貫して伝えてきた「AIに考えさせるのではなく、自分の思考をAIで拡張する」という考え方とも、深いところでつながっています。

## まとめ：Dynamic Workflowsで「発注する側」になる

Dynamic Workflowsは、Claude Codeの自律性を一段引き上げる機能です。要点を整理します。

- **仕組み**：Claudeが現場監督となり、数十〜数百体のAIを並列稼働させ、敵対的に検証させてから答えだけを返す
- **核心**：並列ファンアウト・敵対的検証・収束するまでの反復、の3つ
- **起動**：「ワークフローを作って」と頼む／`ultracode`をオン／`/deep-research`を使う。初回は確認画面が出る
- **必須**：Auto Modeとの併用、そしてトークン消費への注意（スコープを絞る・小さく試す・上限指定）
- **実走の教訓**：指定できるのは「成果物の量」だけで「作業量」は指定できない。筆者が出典5件に絞っても裏で99体・82万トークン・3時間が動いた——「絞れば安全」は鵜呑みにしない
- **本命**：非エンジニアの業務（多角的批評・大量処理・ファクトチェック）にこそ可能性がある

「全部自分でやる」から「AIチームに発注する」へ。この転換を体感できるのがDynamic Workflowsです。まずは`/deep-research`で小さなテーマから、自分の手で試してみてください。実際に動かしたときの驚きと、トークン消費の感覚は、記事を読むだけでは得られないものです。

## よくある質問

**Q. Dynamic WorkflowsはOpus 4.8が必須ですか？**
A. いいえ。公式発表は特定モデルに限定しておらず、Claude Codeの既存モデルラインナップで動作します。ただしOpus 4.8と同時公開されており、ワークフローが活きる高難度タスク（セキュリティ監査・大規模移行など）はOpus 4.8が得意とする領域です。

**Q. Proプランでも使えますか？**
A. 使えます。全有料プランで利用可能なリサーチプレビューです。ただしProはデフォルトでオフなので、初回実行前に`/config`の「Dynamic workflows」をオンにする必要があります。トークン消費が大きいため、最初はスコープを絞って試すのが安全です。

**Q. 以前のClaude Codeにあった「ワークフローを作って」と何が違うのですか？**
A. 以前は単なるサブエージェント操作を指す口語表現でした。今回、Claudeが計画を立て、数十〜数百体に展開し、敵対的検証を行い、収束するまで反復する——という具体的な機能として正式実装されました。

**Q. 管理者が組織全体でブロックできますか？**
A. できます。組織管理者はチームのワークフローを無効化できます。Enterpriseではデフォルトで無効化されており、管理者が明示的に有効化する必要があります。

**Q. Auto Modeはワークフロー内のサブエージェントもブロックしますか？**
A. Auto Modeの分類器は、ワークフロー内の各操作も通常セッションと同じように評価します。サブエージェントが本番インフラで破壊的なコマンドを実行しようとすれば、通常どおりブロックされます。安全装置は「操作単位」で働き、「セッションの種類」では区別しません。
