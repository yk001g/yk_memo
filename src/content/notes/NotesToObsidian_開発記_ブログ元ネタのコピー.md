# Apple のメモを Obsidian に1クリックで放り込むアプリを作った

> ブログ用の元ネタ。事実ベースの開発経過・手順・ハマりどころ。ここから記事に整形する想定。
> 見出し・トーンは自由に組み替えてOK。技術的な数字（バイト数など）は実測値。

---

## 0. TL;DR（記事の要約に使う用）

- **作ったもの**：Apple「メモ」で開いているノートを、**Dockアイコン1クリック**で Obsidian の `00_Inbox/` に取り込むmacアプリ。画像も本文中の正しい位置のまま Markdown 化する。
- **構成**：AppleScript（トリガー）→ JXA（クリップボード読取）→ shell（textutil＋pandoc で変換）→ Python（画像処理・保存）の4層。追加インストールは pandoc だけ。
- **最大の山場**：「メモをコピーすると画像入りのRTFD（リッチテキスト）がクリップボードに載る」という**設計の大前提が、実機では半分外れていた**こと。ここを実データで検証して作り直した。
- **教訓**：macの権限（TCC）と、Appleの独自クリップボード形式は、**ドキュメントより実測が正義**。

---

## 1. きっかけと要件

Apple の「メモ」は素早く書けるけれど、Obsidian に持っていくのが地味に面倒。コピペすると書式や画像位置が崩れる。**「メモを開いてワンクリックで、画像ごとObsidianのInboxに入る」**——それだけを、安全第一で実現したかった。

決めた設計原則（ここは最後までブレさせない）：

1. **Vaultの既存構造を一切書き換えない**（すべて `00_Inbox/` 配下に閉じる）
2. **上書き操作ゼロ**（同名は連番、内容が完全一致なら取り込まずスキップ）
3. **無音で失敗しない**（異常時は必ず中断して通知。原因が分かる文言で）
4. **一時ファイルは毎回クリーン**（`/tmp/n2o` を使い捨て）

この4つが、後半のトラブル対応で何度も自分を助けることになる。

---

## 2. アーキテクチャ：なぜ4層に分けたか

「1個のスクリプトで全部やる」こともできたが、**各層を単体でテストできる**ように役割を割った。

```
[Dockクリック]
  └ NotesToObsidian.applescript … トリガー層（メモをコピー・通知・エラー分岐）
       └ read_rtfd.js (JXA)      … クリップボードから本文データを取り出す
            └ convert.sh          … textutil → pandoc で Markdown化＋画像抽出
                 └ ingest.py      … 画像変換・リンク書換・frontmatter付与・保存
```

- **引数レス設計**：層と層の受け渡しは「クリップボード」と、`/tmp/n2o` に置く中間ファイル（`meta.json` など）だけ。呼び出しをシンプルに保つ。
- **設定は1箇所に集約**：`config.sh` の定数（Vaultパス等）と `ingest.py` 冒頭の辞書だけ触れば挙動が変わる。

作る順番も工夫した。**先にテスト台本とREADMEを書き（T5）**、それから下流のデータ処理（read→convert→ingest）を直列で作り、最後にトリガー層（AppleScript）。「動作確認のやり方」を先に決めると、実装がブレない。

## 3. 技術的な見どころ（手順の要点）

### 3-1. クリップボードを pbpaste で読まない（JXA直読）
`pbpaste` はテキストしか取れない。画像入りの本文を取るには、**JXA（JavaScript for Automation）+ ObjCブリッジ**で `NSPasteboard` を直接読む。ここで取れる `com.apple.flat-rtfd`（画像内包のリッチテキスト）を、`NSFileWrapper` で `.rtfd` バンドルに復元する。

### 3-2. 画像位置の保持は textutil → pandoc
`.rtfd` を `textutil -convert html` でHTML化すると、画像が本文の**正しい位置**に `<img>` として並ぶ。これを `pandoc -f html -t gfm-raw_html` で Markdown 化。余計な `<span>`・style は sed で前処理除去。
→ 「本文→画像A→本文→画像B→本文」という**混在の並び順**が保たれるのが肝。

### 3-3. 安全側のファイル処理（ingest.py）
- HEIC は `sips` で jpg 変換（Obsidian描画の安全側）
- 画像は `<ノート名>-<日時>-01.jpg` の形にリネームして `00_Inbox/_attachments/` へ
- **内容ハッシュ（sha256）を frontmatter に埋め、同一なら取込スキップ**（二重取込防止）
- ファイル名が衝突したら `_2`, `_3` と連番（上書きしない）

ここは擬似入力での単体テストを繰り返し、**5点（frontmatter付与／HEIC変換／リンク書換／hashスキップ／連番）**が通ることを確認しながら進めた。

## 4. ハマったところ（記事のメイン。ここが一番おもしろい）

### 4-1. mac の権限（TCC）地獄

アプリはできた。クリックした。**……何も起きない。** 通知すら出ない。

順に切り分けていくと、原因は複数重なっていた。

- **アクセシビリティ権限は「自動で許可ダイアログが出ない」**。このアプリは Cmd+A / Cmd+C のキー操作を送るので**アクセシビリティ権限が必須**なのに、macOSはこれを自動で聞いてこない。手動で「システム設定→プライバシーとセキュリティ→アクセシビリティ」にアプリを追加しないと、**永遠に無言で失敗**する。
- **自動化（Automation）権限が"拒否"で固まると、二度と聞かれない**。一度うっかり拒否扱いになると、macOSはダイアログを再表示せず黙って弾く。`tccutil reset AppleEvents <bundle-id>` でリセットして、はじめてダイアログが復活した。
- **アプリ名が "applet" と表示される問題**。`osacompile` で作ったアプリは Bundle Identifier が未設定だと、権限画面に本来の名前ではなく **"applet"** と出る。他の自作アプリと見分けがつかない。`plutil` で Identifier を付けて `codesign` で署名し直して解決。

> 教訓：**「無音で失敗しない」設計にしていても、通知そのものが権限や集中モードで消える**ことがある。まず「テスト通知が見えるか」から確認するべきだった。

### 4-2. 最大の落とし穴：flat-rtfd に画像が入っていなかった

権限を通したら、今度はアプリが最後まで動くようになった。が——

- **画像入りノート**：文字は取り込めたのに、**画像が `_attachments` に入らない**。
- **テキストのみのノート**：「コピー内容が取得できません（flat-rtfd なし）」で中断。

「flat-rtfd さえ取れれば画像も入る」という**設計の大前提が崩れた**瞬間。ここで、闇雲に直すのではなく、**クリップボードの中身を実測**することにした。

read_rtfd.js に「pasteboard に載っている全型とバイト数をファイルにダンプする」診断機能を仕込み、アプリ自身がメモをコピーした瞬間の実態を記録させた。結果はこうだった：

| ノート種別 | クリップボードの実態 |
|---|---|
| **リンクを貼ったノート** | `flat-rtfd` は **947バイト**（テキストとリンクだけ）。画像の実体は独自形式 `com.apple.notes.richtext` に **1.4MB** で存在。→ flat-rtfd に画像は無い |
| **テキストのみ** | `flat-rtfd` は **無し**。`public.rtf` だけ |
| **写真を貼ったノート** | `flat-rtfd` に **画像ごと入る**（5.4MB／webp5枚を確認） |

**つまり：**
- flat-rtfd は「**添付/画像があるときだけ**」生成される。テキストだけのノートは `public.rtf` になる。
- ただし「リンクプレビューのサムネイル」は画像扱いされず、**Apple独自形式にしか入らない**。だから取れない。
- **本当に写真を貼ったノートは、flat-rtfd に画像がちゃんと入る**（＝アプリの主目的はOK）。

最初に「画像が落ちる」と思ったのは、たまたまテストしたノートが**リンクプレビュー**で、そもそも実画像が無かったから。本物の写真ノートで試したら、**5枚の画像が本文の正しい位置のまま、Vault に取り込めた**。設計の核心（本文＋画像の混在順）は、実機のリアルデータで成立した。

### 4-3. クリップボード経由の診断は難しい

この検証で地味に効いたのが、**「結果を人に伝えるためにコピペすると、クリップボードが上書きされて診断できなくなる」**問題。通知の文言をコピーした瞬間、そこには Chrome由来のデータ（`org.chromium.*`）が載ってしまう。
→ 対策として、**アプリ自身がコピーした瞬間の状態をファイルに残す**方式にした。診断はチャットの外（ファイル）で行う。

### 4-4. テキストノート対応（設計変更）

検証結果を踏まえ、`read_rtfd.js` を **「flat-rtfd（画像入り）→ public.rtf（テキスト）」の順で読む**ように拡張。前者は `.rtfd` バンドル、後者は `.rtf` として書き出し、`convert.sh` はどちらも textutil で処理する。これで**テキストだけのノートも取り込める**ようになった。

`flat-rtfd` は遅延レンダリングで一瞬 nil を返すことがあったので、**UTI名（`com.apple.flat-rtfd`）と旧名（`NeXT RTFD…`）の両方を試す**堅牢化も入れた。

---

## 5. 検証してから作り直す、という進め方

面白いのは、この「画像が入らない/テキストが弾かれる」問題が、**設計段階で"後回し"にしていた検証項目そのもの**だったこと。設計書には「経路①（RTFD）は本文の中身に依存しない」と書かれていたが、それは**未検証の仮定**だった。

実機で1分検証するはずが後回しになり、**実装後にビルド担当が実データで検証して、仮定のズレを発見**——という流れ。ここで大事だったのは、

- 勝手に設計を変えず、**実測データを示して判断を仰いだ**こと
- 「画像欠落＝バグ（直す）」と「テキスト非対応＝設計変更（承認を取る）」を**切り分けた**こと

結果、テキスト対応は承認を得てから追加し、リンクプレビューの限界は**"既知の限界"として文書に明記**した（無理に追わない）。

## 6. 技術スタック / 依存

- **AppleScript**（Dockトリガー・通知・エラー分岐）
- **JXA (JavaScript for Automation) + ObjCブリッジ**（`NSPasteboard` 直読）
- **textutil**（RTFD/RTF → HTML、画像抽出）※macOS標準
- **pandoc**（HTML → GitHub Flavored Markdown）※`brew install pandoc` だけ追加
- **Python 3**（画像処理・sipsでHEIC変換・frontmatter・ハッシュ・保存）※標準ライブラリのみ
- **sips**（HEIC→jpg）※macOS標準

「追加インストールは pandoc だけ」という依存の軽さは、最後まで守った方針。

## 7. できること / できないこと（正直に）

**できる（実機確認済み）**
- 写真・スクショを貼ったノート → 本文＋画像を**正しい位置**で取込
- テキストのみのノート → 取込
- 二重取込の防止（内容ハッシュ）、上書きゼロ、異常時の通知

**できない（既知の限界）**
- **リンクプレビューのサムネイル画像**（実体がApple独自形式にしか無い）
- 表・PDF添付の完全再現（v1では追わない）
- クリップボードの退避・復元（実行中は上書きされる）→ 将来対応

## 8. 学び（記事の締めに使えるやつ）

1. **ドキュメントの仮定は、実測で殴られる。** 「flat-rtfdに画像が入る」は半分しか正しくなかった。早めに1分検証しておけば設計段階で分かった。
2. **macの権限は「自動で聞いてくれる」とは限らない。** アクセシビリティは手動追加が必須。TCCが"拒否"で固まったらリセット。
3. **無音で失敗しない設計は正義。だが通知自体が消える経路も潰す。** テスト通知が見えるかから確認。
4. **層を分けると、実データが無くても各層を単体検証できる。** 権限や実機が絡む部分と、純粋なデータ変換を分離できたのが救いだった。
5. **「バグ修正」と「設計変更」を切り分けて、後者は必ず承認を取る。** 勝手に設計を変えない規律が、最終的な品質を守った。

## 付録：データフロー（図解用メモ）

```
クリック
 → メモをactivate → 本文にフォーカス（G1）→ Cmd+A → Cmd+C
 → read_rtfd.js: flat-rtfd(画像) or public.rtf(テキスト) を取得
      ├ 無ければ中断＋通知（G2）
      └ 空/巨大なら中断＋通知（G3）
 → convert.sh: textutil→HTML→(span除去)→pandoc→capture.md（画像は/tmpに抽出）
 → ingest.py: HEIC→jpg / 画像を_attachmentsへ / リンク書換 / frontmatter＋hash
      ├ 同一hashが既存なら skip＋通知
      └ 名前衝突は連番
 → 「取込完了：〈ノート名〉」通知
 → /tmp/n2o は毎回クリーン
```
