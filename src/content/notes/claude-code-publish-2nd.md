## はじめに(リード文)

**前回記事で書いた「Claude DesignでサイトをつくったYK」が、その後はじめて新記事を本番公開しました。公開作業に約4時間かかった理由は「学びながら進めたから」。次回は30分で済む段取りを、ひとつにまとめます。**

私は八王子・片倉台で月次のスマホ・わいわいサロンを運営している、シニア向けAIリテラシー教育者です。yk_memo というブランドで活動しています。前日の4月26日に、Claude Design・Claude Code・Vercelを使って自分のサイトを構築したばかり。そのサイトに、初めて新記事を1本追加する作業を、今朝(4月27日)実施しました。

この記事を読み終えると、次の3つがわかります。

- 非エンジニアがサイトに記事を追加する全7ステップの具体的手順
- Claude チャットと Claude Code をどう使い分けるかの判断基準
- 404エラーや想定外の挙動に当たった時の、慌てない対処法

> 【現場レポ】2026年4月27日 朝6時から10時にかけての、初めての本番デプロイ作業の体験記です。途中で出会った404エラーや「自動コミット」など、想定外の出来事も含めて、そのまま記録しました。

対象読者は、**前回記事を読んだ40〜60代の自営業・小規模事業主・教育関係者**、そして**自分のサイトをすでに持っていて、これから記事を更新していきたい方**です。Claude Code を初めて触る方にも、雰囲気が伝わるように書きました。

## なぜサイト公開作業を「ひとりでやらない」のか?

**前回記事のサイト構築から1日経って、新記事を公開する作業に入りました。ひとりで進めようと思えばできましたが、Claude Code と二人三脚で進めることを選びました。理由は3つあります。**

サイト構築の翌朝、いよいよ前日に書き上げた27,000字の記事を本番に公開する段階です。サイトを作った経験がある分、「だいたいこんな感じだろう」という見通しはありました。`[slug].astro` を編集して、GitHub に push して、Vercel が自動でビルドする。流れは頭の中で描けます。

でも、結論から言うと、**最初から最後まで Claude Code と二人三脚で進めることを選びました**。これは決して「ひとりではできなかった」からではありません。むしろ、できる範囲のことでも**意図的に Claude に頼った**理由が3つあるからです。

### ひとりで進めると何に詰まるのか?

**ひとりで作業を進めると、最初に詰まるのは「何が分からないか」が分からないことです。サイトの仕組みを完全に把握しているならいいのですが、私のような非エンジニアには、未知の領域がどこにあるかも見えません。**

具体的に、ひとりで作業しようとすると次のようなことが起きます。

- 「どこから手をつけるか」で5分迷う
- 「自分が何を知らないか」が見えないまま進める
- エラーが出た時に、慌てて何かを触ってしまう
- 結果として、状況が悪化する

特に最後の「焦って何かを触る」は、私自身が月次サロンで参加者に**「困った時こそ、手を止めてください」**と何度も伝えていることです。シニア向けのスマホ講座でよく起きるパターン。「画面が変だ」と思った瞬間に、片っ端からボタンを押して、症状を悪化させる。これを技術領域でやると、もっと深刻な事態になります。

### Claude Code に頼むと何が変わるのか?

**Claude Code に作業を頼むと、まず「自分のサイトの構造を、初めて他人に説明してもらう」体験ができます。これだけで、自分が何を知らなかったかが浮かび上がります。**

具体的には、3つの変化があります。

1. **ファイル構造を即座に説明してくれる**:`/notes/` 以下のファイルがどう関連しているか、言語化してくれる
2. **「やるべきこと」を計画として提示してくれる**:いきなり実行ではなく、まず計画を見せてくれる
3. **「やってはいけないこと」も教えてくれる**:「このファイルは触らないでください」と忠告してくれる

特に2番目が、シニア教育者として一番ありがたい点でした。「**まず計画を見せてください**」と頼むだけで、Claude Code は自分の作業内容を全部書き出してくれます。私はそれを見て、違和感があれば修正を依頼するだけ。**「実行する前に確認できる」という安心感**が、作業全体の安全性を一段引き上げてくれます。

### 一番のメリットは「焦らない」こと

**今日の作業を振り返って、Claude Code との二人三脚の最大のメリットは、何と言っても「焦らない」ことでした。状況を共有することで、自分の頭の中が整理される。これは、月次サロンで参加者に伝えていることそのものでした。**

朝の作業中、3回ほど「これは想定外だ」という場面がありました。

- 未コミット変更が10件出てきた瞬間
- 404エラーで記事ページが開けない瞬間
- GitHub Desktop が「No local changes」と表示された瞬間

普段なら、ここで一瞬「やってしまった」と焦ります。でも今日は、毎回**Claude チャットに状況を伝える**という一手を挟みました。すると、自分の頭の中が整理されて、「次に何を確認すればいいか」が見えてきます。

| 場面 | ひとりで進めた場合 | Claude チャットに状況を伝えた場合 |
|---|---|---|
| 未コミット10件の発見 | 慌てて全部 commit してしまうかも | 「これは何のファイルか」を確認できる |
| 404エラー | 何度もリロードを繰り返してしまう | 「サーバーキャッシュかもしれない」と仮説が出る |
| Changes が空 | 「何かを失った?」と不安に | History タブで状況を確認できる |

> 【哲学】月次サロンで「困ったらまずAIに状況を伝えてください。質問の仕方を変えるだけで、答えの質が大きく変わります」と教えています。今日、自分自身がその教えを、4時間にわたって実践した日になりました。**人に教える内容は、自分が一番繰り返し練習する必要がある**。これも、教育者として改めて気づいたことでした。

そして、もう1つ大事なポイントがあります。**「Claude チャット」と「Claude Code」を使い分ける**という考え方です。これが今日の体験を貫く一本の軸でした。次の章で、この使い分けを詳しく整理します。

## 「悩んだらチャット、手を動かすときはCode」とは何か?

**Claude には2つの使い方があります。Claude チャット(Web画面で対話する)と Claude Code(ターミナル経由でファイルを編集する)です。この2つを「悩み」と「実行」で使い分けると、作業が劇的に安全に進みます。これが今日の作業を貫く一本の軸でした。**

前回記事の H2-2 で、Claude Design・Claude Code・Vercel の3ツールの役割分担を書きました。今回はもう一段奥に入って、**Claude そのものの中の役割分担**の話をします。これは前回書ききれなかった、非エンジニアにとって最も大事な「使い方の哲学」です。

### Claude チャットは「考える相棒」

**Claude チャットは、画面で文字を打って対話する、いわゆる「ChatGPTのような」使い方です。状況を整理する、選択肢を出してもらう、意味や背景を聞く、といった「考える作業」に向いています。**

具体的に Claude チャットが向いている場面は次のようなものです。

- 「これは何ですか?」と意味を聞きたい時
- 「どうしたらいいですか?」と方針を相談したい時
- 「○○と××のどちらがいいですか?」と判断材料を欲しい時
- 「なぜ404エラーが出るのですか?」と原因を知りたい時
- 「この記事の構成案を考えてください」と思考の整理を頼む時

Claude チャットの特徴は、**ファイルを変更しない**ことです。あくまで「対話」という形で、考えるための材料を提供してくれます。私が紙とペンで考えるのと同じ感覚で、文字でやり取りができる。これが Claude チャットの本質です。

シニア向けスマホ・わいわいサロンで、私はよく **「困ったらまずAIに状況を伝えてください」** と教えています。この時に念頭にあるのは、まさに Claude チャットのような対話型のAIです。Claude Code ではなく、Claude チャットに「これってどういう意味ですか?」と聞く。これだけで、半分以上の悩みは解決します。

### Claude Code は「手を動かす相棒」

**Claude Code は、ターミナルやエディタを通じて、実際にファイルを編集するAIです。コードを書く、エラーを修正する、ファイル構造を変える、といった「実行作業」に向いています。**

具体的に Claude Code が向いている場面は次のようなものです。

- ファイルを実際に編集してほしい時
- 新しいコードを書いてほしい時
- エラーを修正してほしい時
- 複数ファイルにまたがる変更をしてほしい時
- 「このフォルダのファイルを整理して」と作業を頼みたい時

Claude Code の特徴は、**ファイルを実際に変更する力を持っている**ことです。これは Claude チャットにはない強力な能力です。同時に、これが**慎重に使う必要がある理由**でもあります。

> 【哲学】Claude Code がファイルを変更する瞬間は、「**自分の代わりに手を動かしてもらっている**」感覚です。だからこそ、何を任せるかを毎回明確にする習慣が大事だと感じました。任せるけれど、丸投げはしない。月次サロンで教えるなら、これは「料理人にレシピを伝える」のに近い感覚です。何を作ってほしいかは伝える。でも、台所で勝手に好きなものを作られては困る。

### 使い分けの早見表(初心者向け)

**「悩んだらチャット、手を動かすときは Code」という公式は、慣れないうちは判断に迷うかもしれません。次の早見表を頭に入れておくと、迷う時間が減ります。**

私が今日の作業で実際に使い分けた場面を、表にまとめました。

| 場面・依頼内容 | チャット or Code | 理由 |
|---|---|---|
| 「サイトの仕組みを教えて」 | チャット | 状況を理解したい(変更しない) |
| 「リンク死記事を削除して」 | Code | ファイルを実際に編集する |
| 「404エラーの原因を教えて」 | チャット | 仮説を出してもらいたい |
| 「getStaticPaths を書き換えて」 | Code | コードを変更する作業 |
| 「2記事目の表示方法は3案のうちどれがいい?」 | チャット | 判断材料を整理したい |
| 「Astro プロジェクトを再起動して」 | Code | 実際にコマンドを実行する |
| 「ファイルが肥大化する件、どうすべき?」 | チャット | 方針相談、まだ実行しない |
| 「README に新しい記事のリンクを追加して」 | Code | ファイルを編集する |

ポイントは、**「変更するかどうか」**で判断することです。

- **変更しない** → チャット(対話で考える)
- **変更する** → Code(ファイルを編集する)

これだけ覚えておけば、ほとんどの場面で迷わずに使い分けられます。

### なぜこの使い分けが「安全」を生むのか?

**この使い分けが大事なのは、単に効率が上がるからではありません。**「何が起きるか分からない作業」を「何が起きるか分かる作業」に変えてくれる**からです。これが非エンジニアにとっての最大の安全装置です。**

具体的に、安全性が上がる仕組みを3つ説明します。

#### 1. 「考えるフェーズ」と「動くフェーズ」が分かれる

ひとりで作業していると、考えながら手を動かしてしまいます。エラーが出たら、頭で原因を考えながら、画面のボタンを連打してしまう。これは、シニア向け講座で何度も見てきた失敗パターンです。

Claude を使い分けると、自然と「考えるフェーズ」が独立します。Claude チャットに状況を投げる時、私は手を止めて、文字を打つ作業に専念しています。**この「手を止める」だけで、判断ミスが激減します**。

#### 2. 実行前に「計画」が見える

Claude Code は、依頼を受けると「これからこれをします」と計画を提示してくれることが多いです。これは、ひとりで作業していたら絶対に得られない情報です。**実行前に内容が分かる**というのは、技術作業における安心感の本体です。

「計画を見せてください」と一言頼むだけで、Claude Code はファイル名・行数・変更内容を全て書き出してくれます。私はそれを読んで、違和感があれば「これは違います」と伝えるだけ。この一往復で、不可逆な失敗のほとんどを防げます。

#### 3. エラー時に「何が起きたか」を共有できる

エラーが出た時、ひとりで対処すると「何が起きたか」を自分で言語化する必要があります。これがシニア向け講座で一番難しい部分です。「画面が変だ」「ボタンを押しても動かない」と言われても、原因の特定はできません。

Claude チャットに状況を伝える時、私は自分で言語化します。**「いつ、どこで、何が、どう起きたか」**を文字にする。この作業をするだけで、自分の頭の中も整理されます。Claude が答えを返す前に、自分で気づくこともあります。

> 【現場の判断】月次サロンで参加者に教える時、「画面のスクリーンショットを撮って、AIに渡してみてください」と伝えています。この「状況を渡す」という一手が、解決の8割を占めます。AIが優秀だからではなく、**自分の状況を整理することで、自分自身が答えを見つける**からです。これは技術領域に限った話ではなく、人生全般に応用できる態度だと思っています。

### 前回記事の「ハンドオフが消える」と何が違うのか?

**前回記事で「Claude DesignとClaude Codeを組み合わせるとデザインから実装へのハンドオフが消える」と書きました。今回の「悩んだらチャット、手を動かすときはCode」は、この考え方をもう一段奥に進めたものです。**

ハンドオフが消えるのは、**「同じ Claude が、デザイン作業と実装作業の両方を理解している」**からでした。同じ会話の延長線上で、デザインの意図が実装に引き継がれる。これは前回記事のメインメッセージでした。

今回の使い分けは、その逆方向の話です。「**同じ Claude の中で、考える役割と動く役割を意図的に分ける**」。**なぜ分けるかというと、人間側がコントロール権を保つため**です。

| 観点 | 前回記事(ハンドオフが消える) | 今回(悩んだらチャット、手を動かすときはCode) |
|---|---|---|
| 焦点 | Claude の能力 | 人間側の使い方 |
| 効果 | デザイン→実装の境目が消える | 思考と実行の境目が「あえて」生まれる |
| メリット | 効率化 | 安全性と理解の深化 |
| 対象読者 | サイトをこれから作る人 | サイトを継続的に運用する人 |

つまり、**前回記事は「AIの能力をフル活用する話」、今回は「自分のコントロール権を保つ話」**です。両方とも大事で、両方使い分けるからこそ、シニア教育者としても自分のサイトを育てられます。

ここまで使い分けの考え方を整理しました。次の章から、いよいよ今日の作業を7ステップに分けて、それぞれで「悩んだらチャット、手を動かすときはCode」をどう実践したかを具体的に見ていきます。

## Step B-1 で何を確認すべきか?(ローカル同期と未コミット変更の整理)

**作業の最初は GitHub Desktop を開くだけ、と思っていました。ところが「未コミット変更が10件」という警告が出て、いきなり立ち止まりました。確認してから次の手を打つ、という当たり前のことが、ここでも生きました。**

ここから、今日の作業を7ステップに分けて、各ステップでどう「悩んだらチャット、手を動かすときは Code」を実践したかを具体的に見ていきます。最初は Step B-1、ローカルとリモートの同期確認から始まります。

### GitHub Desktop で何を見るのか?

**Step B-1 では、GitHub Desktop を開いて、3つのことを確認するだけです。難しい操作はありません。ただ、この「確認するだけ」を侮ると、後でつまずきます。**

朝6時24分、Mac mini の前に座って GitHub Desktop を起動しました。確認すべきことは次の3点です。

| 確認項目 | 期待される表示 |
|---|---|
| Current Repository | サイトのリポジトリ名(例: `yk_memo`)が選ばれている |
| Current Branch | `main` が選ばれている |
| Fetch origin の状態 | 最近(数分以内)に同期されている |

特に大事なのは「**Fetch origin**」ボタンを押すことです。これは**「リモート(GitHub上)の最新状態を手元に取り込む」**操作です。一度押すだけで、自分の作業環境が GitHub の最新と一致しているかが分かります。

> 【現場レポ】このボタンを押し忘れると、後の作業で「あれ、変更が反映されない」という事態に陥ります。記事の H2-4 で書く 404 エラーとは別の、もう一段下のレベルでの「同期ズレ」が起きうる。**作業の最初に同期する**は、実は地味だけど大事な習慣です。

### 未コミット変更が見つかった時はどうするか?

**ところが、Fetch origin を押した直後に、想定外の表示が出ました。「Changes 10」という赤いバッジ。手元に未コミットの変更が10件ある、という意味です。**

ここでひとりで作業していたら、おそらく次のどちらかをやってしまいます。

- 「とりあえず全部 commit してしまおう」と一括処理
- 「何か壊れたかも」と慌てて discard(変更を破棄)してしまう

どちらも、**取り返しがつかない可能性のある操作**です。前者をやると不要なファイルが履歴に残り、後者をやると大事なファイルが消えます。

ここで採った手順は、**「悩んだらチャット」**でした。Claude チャットに「未コミット10件が出てきた、どう対処すればいいか」と相談する前に、まず**自分で状況を見る**ことから始めました。

具体的には、Changes タブを開いて、10件のファイル名を見ました。何も触らずに、ただ見るだけ。その時点で「これは前日にダウンロードした記事原稿のチャンクファイルだ」と気づけました。

> 【哲学】月次サロンで参加者によく言うのは、「困った画面が出ても、まず操作しない。3秒間、画面を見つめてください」です。今日、自分自身がそれを実践しました。**画面を見つめる3秒**で、原因の半分は分かることが多い。

### 10ファイルの正体は何だったか?

**10ファイルは、前日に Claude.ai からダウンロードした記事原稿のチャンク7本+統合版+補足解説章+ビルドログPDFでした。これらは「サイトを動かすファイル」ではなく、「素材・参考資料・原稿」です。**

つまり、サイトのリポジトリの中に、**役割の違うファイルが混在していた**状態です。これは、サイトの動作には影響しません。でも、放置すると将来の問題の種になります。

| ファイル種別 | サイトとの関係 | あるべき場所 |
|---|---|---|
| `src/pages/index.astro` | サイトを動かすコード | リポジトリ内 ✅ |
| `src/styles/global.css` | サイトを動かすコード | リポジトリ内 ✅ |
| `package.json` | サイトを動かす設定 | リポジトリ内 ✅ |
| `article_chunk_01.md` 〜 `_07.md` | 記事原稿 | リポジトリ外が望ましい |
| `yk_memo_article_final.md` | 記事原稿(統合版) | リポジトリ外が望ましい |
| `yk_memo_site_build_log.md.pdf` | 作業ログ | リポジトリ外が望ましい |

10件は全て後半の「原稿・ログ系」でした。

### なぜ「Bプラン」を選んだか?

**未コミットの10件をどう扱うかには、3つの選択肢がありました。私が選んだのは「B案:別の場所に移動して、リポジトリから取り除く」でした。理由は3つあります。**

選択肢を整理します。

- **A案**: そのまま commit する → サイトリポジトリが原稿で肥大化していく
- **B案**: 別場所(Projects フォルダ)に移動 → サイトリポジトリから取り除く(採用)
- **C案**: `.gitignore` で Git の管理外にする → ファイルは残るが追跡対象から外れる

A案の問題は、**「サイト本体」と「原稿置き場」が混在する**ことです。記事を1本書くたびに、原稿のチャンク10ファイルがリポジトリに増えていく。これは長期的にはサイトの管理コストを上げます。

C案は中途半端です。フォルダの中に「Git追跡されているファイル」と「無視されているファイル」が混在することになり、後で混乱の元になります。

B案を選んだ理由は3つあります。

1. **YK の普段のワークフローと合う**:Obsidian で書いて、必要なものだけサイトに反映する流れ
2. **「役割分担」のメッセージと一致**:今回の記事のテーマ「役割分担を明確にする」と同じ思想
3. **将来の拡張性**:サイトをいずれ Content Collections 化する時、原稿が別場所にある方がスムーズ

> 【現場の判断】こういう「整理の方針」は、Claude Code に頼まず Claude チャットで相談しました。**ファイルを動かす作業ではなく、判断する作業**だからです。Claude Code に「整理してください」と頼むと、勝手な判断で動かされる可能性があります。考える作業はチャット、動く作業は Code、という使い分けが、ここでも生きました。

### Finder での移動の落とし穴は何か?

**「別の場所に移動する」だけの作業ですが、Mac の Finder には1つだけ落とし穴があります。それは「ドラッグ&ドロップが、コピーになるか移動になるか分かりにくい」ことです。**

Mac の Finder では、**異なるディスク間のドラッグ&ドロップは「コピー」**になります。つまり、元のファイルが残ります。これに気づかずに作業を進めると、**「ファイルが2箇所に存在する」状態**になり、後で混乱します。

確実に「移動」にする方法は1つだけ。**`Command キーを押しながらドラッグ&ドロップ`** すること。これで必ず移動になります。

確認方法も覚えておくと安心です。

- **移動の場合**:ドラッグ中、ファイルアイコンに「+」マークが**つかない**
- **コピーの場合**:ドラッグ中、ファイルアイコンに「+」マークが**つく**

私の場合、`Command` を押しながらドラッグして、10ファイルを Projects フォルダ内の新規フォルダ(`2026-04-26_claude-design-blog-article`)に移しました。元のフォルダ(`files20260426a/`)が空になったのを Finder で確認してから、ゴミ箱に入れました。

### Step B-1 の成果は何だったか?

**Step B-1 が終わった時点で、GitHub Desktop は「No local changes」になりました。当初の目的「ローカルとリモートの同期確認」に加えて、未コミット10ファイルの整理という想定外のボーナス作業も完了したことになります。**

| 項目 | 開始時の状態 | 終了時の状態 |
|---|---|---|
| Fetch origin | 古い | 最新 |
| Changes タブ | 10件の未コミット変更 | 0件(クリーン) |
| 原稿ファイルの場所 | リポジトリ内 | Projects 内に整理 |
| 心理状態 | 「何か変更がある?」と不安 | 「整理できた」と安心 |

ここまで約30分。記事のメインの作業はまだ始まっていませんが、**作業環境を整える**という大事な準備が完了しました。

> 【哲学】料理に例えると、Step B-1 は「**まな板を綺麗にする**」工程です。料理の味には直接影響しないけれど、これをやっておくと後の作業がスムーズになる。雑だと、肝心な時に「あれ、置く場所がない」となる。技術作業も全く同じで、**始める前の整理が、後の効率を決めます**。

次の Step B-2 では、いよいよ Claude Code に初めての編集作業を頼みます。「リンク死5本を一覧から削除する」作業を通して、**Claude Code に依頼するときの「型」**を学びます。

## Step B-2 でリンク死記事をどう削除するか?(Claude Codeに頼む計画→OK→実行の3段階)

**サイトの一覧ページには8本の記事タイトルが並んでいましたが、5本はクリックしても飛べない予告状態でした。これを削除する作業を、初めて Claude Code に頼みました。頼み方の「型」を覚えると、安全に作業を進められることを実感しました。**

朝7時、いよいよ Claude Code に最初の編集作業を依頼します。これは**今回の作業全体で初めて「ファイル変更を伴う依頼」**でした。前回記事の H2-4 で書いた「Claude Codeに状況を説明すれば、ほぼ確実に解決した」を、今度はもう一段深く実践する場面です。

### 「リンク死5本」は何だったのか?

**「リンク死」とは、記事一覧には載っているのに、クリックしても記事ページに飛べない状態のことです。私のサイトでは、開発時にタイトルだけ予告として並べた5本が、この状態で長期間放置されていました。**

具体的には、次のような状態です。

| タイトル | 一覧表示 | リンク先 | 記事ページ |
|---|---|---|---|
| Gemini で音楽を作る 5 分間 | あり | `href="#"`(飛べない) | なし |
| AI と競争しない、という選択 | あり | `href="#"`(飛べない) | なし |
| ボランティア生徒さんの一年を振り返って | あり | `href="#"`(飛べない) | なし |
| Obsidian を使い始めて 3 年 | あり | `href="#"`(飛べない) | なし |
| シニアにとって「調べる」とはどういうことか | あり | `href="#"`(飛べない) | なし |

つまり、**「設計図(一覧)だけ先に描いて、ページ本体はまだ作っていない」**状態です。よくある初期立ち上げあるあるですが、訪問者にとっては混乱の元です。クリックしても何も起きない記事を見せられても、「これは何なんだろう」となるだけです。

### 削除作業を Claude Code に頼む型とは何か?

**Claude Code に複雑な作業を頼むときには、「探検 → 計画 → 実行」の3段階で進めるのが安全です。これが今日学んだ最大の型でした。**

3段階の意味は次の通りです。

#### 段階1:探検

「これからこういう作業をしたいので、まず現状を教えてください」と Claude Code に状況把握を頼む段階。**まだ何も編集しない**ことを必ず明示します。

#### 段階2:計画

「現状が分かったので、編集計画を立ててください」と、変更内容の計画を提示してもらう段階。ここでも**まだ何も編集しない**。私が計画を見て、違和感があれば修正を依頼します。

#### 段階3:実行

私が「OK、計画通りに進めてください」と返事をしてから、初めて Claude Code が実際の編集を実行する段階。

> 【哲学】この3段階は、シニア向けスマホ講座でよく使う「**やる前に、口で説明してもらう**」と同じ手法です。受講者の方に新しい操作を教える時、すぐに画面を触らせるのではなく、「**まず何をするか、口で言ってみてください**」と促す。これだけで、操作前の理解度が格段に上がる。Claude Code への依頼でも、全く同じことが言えます。

### 削除依頼プロンプトの3つの工夫とは何か?

**Step B-2 で実際に Claude Code に送ったプロンプトには、3つの工夫を入れました。これらは他の作業でも応用できる「型」になります。**

私が使ったプロンプトの抜粋を紹介します(全文は長いので一部だけ)。

```
src/pages/notes/index.astro ファイルの記事一覧から、
リンク先が href="#" になっている記事(=クリックしても飛べない予告記事)を
5本まとめて削除したいです。

【背景】
これらの5本はタイトルだけ予告として並べていましたが、
記事ページ([slug].astro)に登録されておらず、
クリックしても遷移できない状態が長期間続いています。

【削除対象】
href="#" になっている記事ブロックすべてです。
具体的には次の5本(順不同):
- Gemini で音楽を作る 5 分間
- (以下省略)

【残すもの】
href="/notes/[slug]/" の形でリンクが正しく
設定されている記事3本(...)はそのまま残してください。

【作業前にお願いしたいこと】
1. 編集前に、削除対象の5本がどの行にあるかを示してください
2. その後、編集計画(どのブロックを消すか)を提示してください
3. 私が「OK」と返事してから、実際の編集を実行してください
```

このプロンプトには3つの工夫が入っています。

#### 工夫1:背景を伝える

「なぜ削除するか」を伝えると、Claude Code が**「ついでにこういう改善もしましょうか」と提案してくれる**ことがあります。「削除して」だけだと、機械的な作業になってしまう。背景を伝えることで、**Claude Code の判断力を引き出せる**のがポイントです。

#### 工夫2:削除対象と保持対象を両方明示

「~を消して」だけだと、もしファイル構造を誤解した時に**保持したいものまで消えてしまう**リスクがあります。「**これは消す、これは残す**」と両方明示すると、片側の理解違いが起きても、もう片側で気づける。**安全のための二重確認**です。

#### 工夫3:「実行前に確認させてください」を入れる

これが最も大事です。**Claude Code は依頼すると、設定によっては即実行することがあります**。「計画を見せて → OK返事 → 実行」というワンクッションを入れることで、想定外の編集を防げます。

### Claude Code が見せてくれた優秀さとは何だったか?

**Claude Code はプロンプトを受けて、想像以上に細やかな計画を返してくれました。特に印象的だったのは「セクションごと削除する」という発見です。**

返ってきた計画の要点は次の通りです。

- 削除する5本のうち、3本がすべて 2025 セクション内に含まれていた
- そのため、`<li>` 単位ではなく、`<section>` ごと削除する判断
- 結果として、「2025年」という年見出しも消える

私自身は、最初「`<li>` を5つ削除する」という素朴な発想でした。Claude Code は**「2025年のセクション全体が空になる」ことを見抜いて、より構造的な削除を提案**してくれた。これは、ひとりで作業していたら気づかなかった視点です。

もう1つ印象的だったのは、**タグフィルターの `href="#"` を残してくれた**ことです。

> 残っている `href="#"` はタグフィルター(すべて・AI・教育…)のボタン部分だけで、記事リンクには # は一切ありません。意図した状態です。

私はプロンプトで「`href="#"` の記事を消して」とは言っていません。「`href="#"` になっている**記事**ブロックすべて」と書いた。Claude Code はこの違いを理解して、**「記事リンク」と「タグフィルターのボタン」を区別**してくれた。後者を消すと、サイトの機能が壊れます。**この見極めができるのが、Claude Code の真の価値**です。

> 【現場レポ】Claude Code の計画を読みながら、「あ、こういう視点があったのか」と何度も気づかされました。**自分の視野の死角を、AIが補ってくれる**感覚です。これは月次サロンで参加者に伝えたい体験でした。

### 完了報告で何を確認するかは何か?

**実行依頼の時に、報告項目を5つ指定しました。「OK」だけで送るのではなく、「以下を報告してください」を加えるのが、後の確認を楽にするコツです。**

私が指定した報告項目はこうです。

```
削除後、編集が完了したら次のことを教えてください:
1. 削除した行数の合計
2. 編集後のファイルの総行数
3. 残った記事3本のリンク先(href)が正しいことの確認
```

これは「**作業前に検収条件を決める**」というプロジェクト管理のテクニックです。**作業させた後、自分で確認するための数字を出してもらう**のが、安全な使い方の基本パターンになります。

返ってきた報告:

| 確認項目 | 結果 |
|---|---|
| 削除行数 | 25行 + 43行 = 68行(計算合致) |
| 総行数 | 305行 → 237行 |
| 残ったリンク | 全て `/notes/[slug]/` 形式で正しい |

すべて想定通りでした。これで Step B-2 の実行段階は完了です。

### Step B-2 の振り返り

**Step B-2 を通して学んだのは、「Claude Code への依頼は、プロンプト文の質で 7 割決まる」ということでした。雑な依頼には雑な結果、丁寧な依頼には丁寧な結果が返ってきます。**

今日のプロンプトで使った3つの工夫は、これからのどんな編集作業でも使える「型」になりました。

| 場面 | 使う工夫 |
|---|---|
| 削除作業 | 削除対象 + 残す対象を両方明示 |
| 追加作業 | 既存の構造を確認させる |
| 修正作業 | 修正前後を例示する |
| 整理作業 | 何を整理するか + 整理しないものも明示 |

> 【失敗談】「OK」だけ返してしまうと、確認漏れが起きます。実行依頼の時には必ず「以下を報告してください」と項目を5つくらい挙げて、検収条件を先に決めるのがコツです。**確認は、作業の前にこそ準備するもの**だと、改めて気づきました。

ここまでで、Step B-1(同期と整理)と Step B-2(リンク死削除)が完了しました。次の Step B-3 では、いよいよ今日のメインイベント、新記事の追加作業に入ります。**3つのファイルを同時に編集する**という、今までより複雑な作業になります。

## Step B-3 で新記事をどう登録するか?(3ファイル独立構造への対応)

**いよいよ、前回書いた27,000字の記事を本番サイトに登録します。ここで判明したのは「3つのファイルがそれぞれ独立して記事リストを持っている」という設計でした。ひとつの記事を追加するのに3箇所を更新する必要がある現状の仕組みも、Claude Code に頼めば一気に進められます。**

朝8時、Step B-3 に入りました。今日の作業の中で最も複雑で、最も時間のかかる工程です。前回記事の H2-4「7箇所のつまずき」のうち②(HTML→Astro変換)と類似した作業を、今度は本番サイトの記事追加として実演する場面です。

### 登録前に決めることは何か?

**Claude Code に作業を頼む前に、人間側で決めておくことが7項目あります。これを先に決めておくと、Claude Code との対話が驚くほどスムーズに進みます。**

私が事前に決めた項目はこうです。

| 項目 | 決め方 | 私の場合 |
|---|---|---|
| 原稿パス | Claude Code が読める場所を指定 | `../Projects/2026-04-26_xxx/yk_memo_article_final.md` |
| スラッグ(URL末尾) | 英数小文字+ハイフン区切り | `claude-design-1day-build` |
| date | 記事の内容に合わせる | `2026-04-26` |
| dateDisplay | 表示用の日付フォーマット | `2026.04.26` |
| tags | 既存タグ体系に合わせる | `['道具', '教育']` |
| description | リード文から120字に圧縮 | (Claude が抽出) |
| 一覧表示 | 普通に追加 or 既存記事との関係 | 今回の記事だけ追加 |

これは月次サロンで参加者によく言う **「料理の段取りと同じ」** です。包丁を握る前に、何を作るかを決めておく。買い物リストを作っておく。これがないと、調理を始めてから「あ、塩がない」と気づいて止まる。Claude Code に頼む作業も同じで、**事前準備の段取りで作業時間が半減**します。

### なぜ「探検 → 計画 → 実行」の3段階で進めるのか?

**Step B-2 で確立したこの3段階は、新記事追加でも同じく重要です。むしろ、編集箇所が増える分、もっと重要になります。**

3段階のメリットを、改めて Step B-3 の文脈で整理します。

#### メリット1:いきなり「やって」と頼まない

新記事追加では、3つのファイルを変更します。`[slug].astro`(記事本体)、`notes/index.astro`(一覧ページ)、`index.astro`(トップページの Recent Notes)。**それぞれ別の構造で、別の場所に追加が必要**です。

これをいきなり「やって」と頼むと、Claude Code は「分かりました」と作業を始めます。でも、私の頭の中にあった「こういう感じで」と Claude の解釈にズレがあった場合、**3つのファイルが全部間違った状態になります**。後から戻すのが大変です。

#### メリット2:計画段階で違和感を見つけられる

第2段階で計画を見せてもらうと、私は次のような違和感を見つけられます。

- 「このフロントマター項目、既存記事と書き方が違うな」
- 「この description、SEO観点で長すぎないか?」
- 「この場所に追加すると、デザインが崩れるかも」

これらは**実行後では戻すのが大変**です。計画段階なら「この部分、こう変えてください」と一言伝えるだけで修正できます。

#### メリット3:実行前に修正できる余地を残す

これが最も大事です。**人間が判断する余地を残す**こと。Claude Code が優秀になればなるほど、人間側の判断機会が減ります。意識的に「実行前の確認段階」を作らないと、いつの間にか全部任せきりになる。

> 【哲学】月次サロンで参加者によく言うのは、「**AIに任せる勇気と、最後は自分で判断する責任**は、両立できます」です。Step B-3 の3段階は、まさにこの両立を実現する仕組みでした。

### 第1段階(原稿の読み込み依頼)で何を聞くか?

**最初に Claude Code に頼むのは、「原稿ファイルを読み込んでください、ただし、まだ何も編集しないでください」という依頼です。これは「探検」の段階です。**

私が実際に送ったプロンプト:

```
これからこのサイトに新しい記事を1本追加する作業をします。

【原稿の場所】
../Projects/2026-04-26_claude-design-blog-article/yk_memo_article_final.md

【作業の前にお願い】
まず、上記のファイルを読み込んで、以下を教えてください:

1. ファイルが正しく読めたか(冒頭のタイトルと文字数の概算)
2. 原稿の章構造(H1, H2の見出し一覧)
3. ファイル末尾にコメントブロック(<!-- -->で囲まれた部分)があれば、
   それが何の情報か

この段階では、まだ何も編集しないでください。
読み込みと内容把握だけお願いします。
```

このプロンプトには4つの工夫が入っています。

#### 工夫1:「ファイルが正しく読めたか」を最初に確認

パスが間違っていたら、ここで判明します。**先に進む前に必ず確認したい情報**です。私のサイトリポジトリの上の階層にある原稿フォルダを参照する形だったので、相対パスが正しく解決されるかが心配でした。

#### 工夫2:章構造を出力させる

これで Claude Code が**ファイル全体を把握している**ことが分かります。中途半端に冒頭だけ読んで作業されるリスクを減らせます。

#### 工夫3:コメントブロックの存在を確認

統合版の末尾には、要ファクトチェックリストの `<!-- -->` ブロックが残っているはずでした(前日に YK が削除済みでしたが、確認のため)。**これを記事に含めない**ことを後で指示する伏線です。

#### 工夫4:「まだ編集しないで」を明示

最重要です。Claude Code は気を利かせて先回りすることがあるので、釘を刺します。「**まず読むだけ**」と明示することで、想定外の編集を防げます。

### 第2段階(計画依頼)で出てきた発見とは?

**読み込みの確認が取れた後、第2段階で「変換と登録の計画」を立ててもらいました。ここで、サイトの構造に関する重要な発見が3つありました。**

最初の発見は、**3つのファイルがそれぞれ独立して記事リストを持っている**ということでした。

#### 発見3:3つの案文を別の角度で抽出してくれた

description / lede / article-summary の3つを、用途別に長さと角度を変えて作ってくれました。

| 用途 | 文字数 | 強調された角度 |
|---|---|---|
| description(SEO・検索結果) | 約105字 | 「ゼロから1日で公開できる」 |
| lede(記事ヘッダー) | 約102字 | 「実体験レポート・再現手順」 |

> 【現場レポ】3つの案文を並べて見ると、Claude Code が**用途を理解した上で角度を変えている**ことが分かりました。これは AI の表面的な仕事ではなく、**コンテンツの目的を踏まえた書き分け**です。月次サロンで「同じことを違う言葉で言い換える練習をしましょう」と教えていますが、AI が一発でやってくれる時代になりました。

### article-summary を自分で修正した理由は何か?

「シニア教育者」という6文字を入れただけ。でも、これが**この記事を他の技術系記事と差別化する核**でした。記事一覧で読者が最初に目にする部分に、私らしさを込める。これは前回記事の H2-6 で書いた「**作品の所有権は、最後まで人間の側にある**」の実演です。

> 【哲学】Claude Code は私が伝えた「対象読者・40〜60代」を理解した上で案文を書いてくれました。でも、「シニア教育者」という固有の立ち位置までは指示していなかった。**自分の声を Claude の声に上書きする一言**を、忘れずに入れる。これが AI 時代の編集者としての最低限の仕事だと思っています。

#### 想定外2:編集確認の許可ダイアログ

> 【現場の判断】「便利さ」と「コントロール権」は、技術ツールを使う上でいつもトレードオフです。「2. Allow all」を選ぶと作業はスムーズに進みますが、**自分が何を承認したか分からなくなる**。月次サロンで参加者に「便利な設定の落とし穴」として伝えられる教訓になりました。

## Step B-4 のローカルプレビューで何が見つかるか?(404エラーの真犯人)

**ローカルサーバーで `http://localhost:4321/` を開いて確認しました。新記事のページにアクセスすると、まさかの 404 Not Found。ここで判明した「Astro のビルドキャッシュ」という現象が、今日一番の学びになりました。**

朝9時前、Step B-3 の編集が完了して、いよいよローカルプレビューで確認する段階に入りました。Antigravity の中でローカルサーバーを起動し、ブラウザで `http://localhost:4321/` を開く。前回記事の H2-3 フェーズ4で書いた「`yk-memo.vercel.app` が開いた瞬間が一番印象的だった」を、今度は本番前のローカル確認で味わうつもりでした。

ところが、新記事のページにアクセスした瞬間、画面に出たのは **「404 Not Found」**。

### ローカルプレビューで何を見るのか?

**ローカルプレビューで確認すべきは、5つの場所です。一つずつ順番に見ていくのが、漏れを減らすコツです。**

確認項目を表にまとめると次の通りです。

| 確認場所 | URL | チェック観点 |
|---|---|---|
| トップページ | `http://localhost:4321/` | サイト全体が崩れていないか |
| 記事一覧 | `http://localhost:4321/notes/` | 新記事が一番上に出ているか |
| 新記事ページ | `http://localhost:4321/notes/[新スラッグ]/` | 本文が読めるか |
| 既存記事 | 各既存スラッグ | 影響を受けていないか |
| スマホ表示 | 開発者ツールでスマホサイズに切替 | レイアウトが崩れていないか |

最初の3つを順番に見ていって、3つ目で問題が起きました。

### 404 が出た時に何を試したか?

**新記事のページにアクセスしたら、404 Not Found が表示されました。一覧ページには新記事のタイトルが正しく表示されているのに、リンクをクリックすると遷移できない。この「片側だけ問題」が、今日の難所でした。**

私が試した対策を時系列で書きます。

#### 試行1:ハードリロード(`Cmd + Shift + R`)

最初に試したのはハードリロードです。前回記事の H2-4 つまずき⑥(ブラウザキャッシュ)で書いた手法。**結果は変わらず**。404のままでした。

#### 試行2:シークレットウィンドウで確認

`Cmd + Shift + N` でシークレットウィンドウを開いて、新記事のURLを直接打ち込みました。これでブラウザのキャッシュは完全にクリアできるはず。**結果は変わらず**。404のまま。

#### 試行3:ローカルサーバー再起動

これが決定打でした。Antigravity 内で動いていた `npm run dev` を一度停止して、もう一度起動する。Claude Code に再起動を頼んでから、再度ブラウザでアクセス。**今度は正しく記事ページが表示されました**。

### 真犯人は「ビルドキャッシュ」だった

**404 の真犯人は、ブラウザのキャッシュではありませんでした。Astro のサーバーが起動時に「どのページを生成するか」を記憶していて、その記憶が更新されていなかったのです。専門的には「ビルドキャッシュ」と呼びます。**

仕組みを説明します。

Astro という仕組みは、起動時に `getStaticPaths` という設定を読み込みます。これは「**どのURLでページを作るか**」の一覧です。私のサイトでは、これに `claude-skills-kyozai` `salon-ai-hajimete` `notebooklm-mcp-cli` の3つが登録されていました。

サーバー起動中に、Claude Code が `getStaticPaths` に4つ目(`claude-design-1day-build`)を追加しました。**でも、サーバーは「最初に決めた3ページ分のルーティング」を保持し続ける**。新スラッグでアクセスしようとしても、「そんなページは知らない」と返事するのが 404 でした。

### 「変更が反映されない」5つの層とは何か?

**サイト開発で「変更が反映されない」を引き起こす原因は、5つの層に分けて考えると整理しやすいです。これは今回の経験から確立した「公式」のひとつです。**

5つの層を、出発点(コード編集)から到着点(画面表示)まで並べると、こうなります。

```
[ ① コード ] → [ ② ファイル保存 ] → [ ③ ビルド ] → [ ④ サーバー ] → [ ⑤ ブラウザ ] → [ 👁 画面 ]
```

各層で「古い情報を覚えている」可能性があり、それが「変更が反映されない」の原因になります。

| 層 | 原因 | 症状の特徴 | 主な対策 |
|---|---|---|---|
| ① エディタ未保存 | `Cmd + S` 押し忘れ | ファイル名に●マーク | 保存する |
| ② ファイルシステム遅延 | 書き込み遅延(秒未満) | 稀 | 数秒待つ |
| ③ Astroビルドキャッシュ | `getStaticPaths` の更新非反映 | 404 が多い | サーバー再起動 |
| ④ HMRの限界 | ルーティング変更は対象外 | 構造変更時 | サーバー再起動 |
| ⑤ ブラウザキャッシュ | 古いページ表示 | 文章・スタイルが古い | ハードリロード |

今回の 404 は、**層③ が真犯人**でした。私が最初に試したハードリロードは層⑤への対策、シークレットウィンドウも層⑤への対策。これらでは層③の問題は直りません。

### HMR(自動反映)の限界とは何か?

**普段の作業では、ファイルを保存すると自動で画面が更新されます。これを HMR(Hot Module Replacement)と呼びます。便利ですが、苦手な変更があります。**

HMR が得意・不得意な変更を表にすると、こうなります。

| 変更の種類 | HMR で反映? |
|---|---|
| 本文のテキスト | ✅ 即反映 |
| `<h2>` などの見出し追加 | ✅ 即反映 |
| CSS 変更 | ✅ 即反映 |
| **`getStaticPaths` の変更** | ❌ **再起動必要** |
| **新しいルート(URL)の追加** | ❌ **再起動必要** |
| `package.json` の変更 | ❌ 再起動必要 |
| 設定ファイル変更 | ❌ 再起動必要 |

**「サイトの構造を変える変更」は HMR の守備範囲外**です。逆に言うと、**「文章を変えるくらい」なら HMR が即時反映してくれる**。これが、私が普段「保存しただけで画面が更新される」と感じていた理由でした。

> 【失敗談】最初は「ハードリロードで直る」と思い込みました。実は **404 はサーバー側の問題**なので、ブラウザのキャッシュをいくらクリアしても直らない。**404 はサーバー側、変な表示はブラウザ側**、という公式が頭に入りました。これは、月次サロンで参加者に教えるとき、必ず役立つ教訓になります。

### 公式:URL構造を変えたら、サーバーを再起動する

**今日の経験から、頭に残しておくべき公式が一つできました。「URL構造を変えたら、サーバーを必ず再起動する」です。**

この公式を分かりやすく整理すると、こうなります。

| 変更内容 | サーバー再起動 |
|---|---|
| 文章を直す | 不要(HMR で反映) |
| 見出しを変える | 不要(HMR で反映) |
| CSS の色を変える | 不要(HMR で反映) |
| **新しいページのURLを追加** | **必要** |
| **`getStaticPaths` の変更** | **必要** |
| **設定ファイル(`astro.config.mjs`等)の変更** | **必要** |

迷ったら **「URL に関わる変更かどうか」** で判断する。URL に関わるなら、サーバー再起動。これだけ覚えておけば、404 で慌てる時間が減ります。

### トップページでも別の問題が見つかった

**新記事ページの 404 を解決した後、サイトを巡回していると、もう一つ問題が見つかりました。トップページの「Recent Notes」セクションに、新記事が出ていない。**

確認すると、次のような状態でした。

| 表示位置 | 新記事の表示 |
|---|---|
| トップページの Recent Notes | ❌ 出ていない |
| `/notes/`(記事一覧) | ✅ 出ている |
| `/notes/[新スラッグ]/`(個別) | ✅ 出ている |

3つのうち、1つだけ古い情報のまま。これは Step B-3 の発見「**3つのファイルがそれぞれ独立して記事リストを持っている**」設計の影響でした。トップページの `index.astro` だけ、まだ更新していなかったのです。

ここでまた **「悩んだらチャット」** に戻りました。Claude チャットに偵察を依頼して、トップページの構造を調べてもらう。すると、こんな修正案が3つ提示されました。

- A案:ハードコードリストの先頭に新記事を追記、最古を1件削除して3件維持
- B案:4件すべて並べる
- C案:`articles` オブジェクトを共有モジュール化(将来向け)

私は **A案(計画通り、最古を削除して3件維持)** を選びました。理由は「**最初から完璧を目指さない**」**動くものを優先**」という前回記事の精神そのものでした。Content Collections 化(C案に近い設計改善)は、次回検討する課題として持ち越し。

> 【哲学】3つのファイルが独立に記事リストを持つ設計は、「**いずれ改善が必要だが、今すぐではない**」という典型的な技術的負債です。月次サロンで参加者によく言うのは、「**完璧を目指すと止まってしまう。動くものを優先して、改善は次に回す**」。今日の私自身が、この教えを実演する場面でした。

### Step B-4 の振り返り

**Step B-4 は、今日の作業で最も学びの多い章でした。404エラーが「層③のビルドキャッシュ」だと判明したこと、トップページが3つの記事リストの一つだと判明したこと、両方とも将来的に何度も出会うテーマです。**

学びを「公式」として整理すると次のようになります。

| 公式 | 内容 |
|---|---|
| 公式1 | URL構造を変えたら、サーバーを再起動する |
| 公式2 | 404 はサーバー側、変な表示はブラウザ側 |
| 公式3 | 「最初から完璧を目指さない」「動くものを優先」 |

> 【現場レポ】404 が出た瞬間、心のどこかで「やってしまった、何かを壊した」という焦りが走りました。でも、そこで止まって状況を Claude チャットに伝えたことで、原因が層③だと特定できた。**慌てて何かを操作する前に、状況を共有する**は、技術トラブル全般に通じる態度だと改めて感じました。

ここまでで、ローカル環境では完全に意図通りの状態になりました。次の Step B-5 では、いよいよ GitHub に変更を送信する段階です。**ところが、ここでまた想定外の事態が起きます**。

## Step B-5 で起きる「想定外の発見」とは何か?(自動コミット問題)

**ローカル確認が終わって、いよいよ GitHub Desktop で commit & push の段に入ります。ところが、Changes タブを開いたら「No local changes」の表示。Claude Code が編集の途中で、すでに自動的に commit まで実行してくれていたのです。**

朝9時48分、ローカルプレビューでの確認が全て完了し、いよいよ GitHub Desktop に切り替えました。前回記事の H2-3 フェーズ4で書いた「コードを書き終えてから本番公開までが、たった1時間」を、今度は記事追加の文脈で実演する場面のはずでした。

### GitHub Desktop で見える「想定外」とは?

**GitHub Desktop を開いた瞬間、画面に出たのは「No local changes」の表示。本来なら3つのファイルが変更されているはずなのに、未コミットの変更がゼロ件になっていました。**

私の頭は一瞬パニックになりました。

- 「ファイルが変更されていないのか?」(でも、ローカルプレビューでは新記事が見えていた)

ここで、再び **「悩んだらチャット」** に戻りました。Claude チャットに状況を伝えて、可能性を3つ整理してもらいました。

| 可能性 | 確認方法 |
|---|---|
| ① すでに別経路で commit & push されている | History タブを見る |
| ② 別のリポジトリを見ている | Current Repository を確認 |
| ③ ローカルプレビューが別の場所のファイルを見ていた | コミット履歴を確認 |

「History タブを見る」が最初の一手と判断しました。

### History タブで見えた事実

**History タブを開くと、画面の一番上に新しいコミットがありました。「Add notes: シニア教育者がClaude Designで個人HPを1日で作った話」というメッセージで、4分前に作成されていました。**

詳細を見ると、こうでした。

### なぜ自動でコミットされたのか?

**Claude Code には「ファイル編集の後、変更を git に反映する」機能があります。今日のどこかのタイミングで、この機能が発火していたようです。**

おそらく、Step B-3 の許可ダイアログで「Yes」を選んだ前後に、Claude Code は次のような一連の操作を実行していたと推測されます。

1. ファイルを編集
2. `git add` で変更をステージング
3. `git commit` でコミットを作成
4. (場合によっては `git push` まで)

驚いたのは、**コミットメッセージが適切な形式**だったことです。「Add notes: ~」という英語の慣習に沿ったメッセージで、私が前日にやった「Initial commit: ~」と一貫した書き方になっていました。**Claude Code は過去のコミット履歴を見て、その書き方に合わせた**可能性があります。

### 自動コミットの「良い面」と「悪い面」

**Claude Code が自動でコミットする機能には、両面があります。今日の作業では結果オーライでしたが、長期的には自分でコントロールする方が学習効果が高いと感じました。**

メリット・デメリットを整理します。

| 観点 | 良い面 | 悪い面 |
|---|---|---|
| 効率 | ◎ 作業がスムーズに進む | - |
| メッセージの質 | ○ 過去履歴に合わせて書く | × 自分の言葉で書く機会を失う |
| 作業履歴の理解 | × どこで何が起きたか追いにくい | ○ 履歴を整理してくれる |
| 学習効果 | × コミット作業の感覚が身につかない | - |
| 安全性 | △ 意図しない commit が作られるリスク | ○ 自動なので作業漏れがない |

特に**学習効果の点では、自分で commit メッセージを書く機会を持つほうが、Git の理解が深まります**。前回記事の H2-7 Q5 で書いた「**文章を保存する感覚で本番が更新される**」を体感するには、自分で commit を打つ経験が必要です。

### 今後どう対処するか?

**Claude Code の自動コミット動作を制御する方法は、依頼時のプロンプトで明示することです。「ファイル編集だけしてください、commit は自分でします」と書けば、Claude Code はそれに従ってくれます。**

次回からは、新記事追加の依頼に1行追加します。

```
【作業の範囲】
ファイル編集のみお願いします。
git add や git commit は実行しないでください。
コミットは私が自分で確認してから実行します。
```

これだけで、コミット作業のコントロール権を取り戻せます。**便利さよりも、自分の理解と判断の機会を優先する**。前回記事 H2-2 で書いた「**作品の所有権は、最後まで人間の側にある**」の応用形です。

> 【哲学】「便利さ」と「コントロール権」は、AI 時代のあらゆる場面で出てくるトレードオフです。月次サロンで参加者によく言うのは、「**便利な機能ほど、無効化する方法を覚えておきましょう**」。Claude Code の自動コミットも同じで、便利だけど、止め方を知っておく。これが安心して使うための前提条件です。

### ハードリロードはなぜ必要なのか?

**本番サイトを確認する時も、必ずハードリロードします。前回見た時のキャッシュが残っている可能性があるからです。**

ハードリロードの方法は、ブラウザによって違います。

| ブラウザ(Mac) | ハードリロードのキー |
|---|---|
| Safari | `Cmd + Option + R` |
| Chrome | `Cmd + Shift + R` |
| Firefox | `Cmd + Shift + R` |

または、**シークレットウィンドウで開く**(`Cmd + Shift + N`)のが最も確実です。シークレットウィンドウは過去のキャッシュを一切持たないので、新規ユーザーがサイトを訪問するのと同じ条件で確認できます。

> 【現場レポ】私は普段、本番確認には Safari のシークレットウィンドウを使います。理由は2つ。①キャッシュの罠を避けられる、②自分の閲覧履歴に「自分のサイトを何度も見た」記録が残らない、つまり**Google Analytics や統計の数字が綺麗になる**。シニア教育者として「自分のサイトの統計をきちんと見たい」時に、ノイズを減らす習慣です。

### もし本番で 404 が出たらどうするか?

**本番URLでアクセスした時に 404 が出る可能性はあります。原因と対処を時系列で考えると、慌てずに乗り切れます。**

|---|---|---|
| Vercel のビルドが終わっていない | Vercel ダッシュボードを見る | 1〜2分待つ |
| Vercel のビルドが失敗した | Deployments タブで Failed 表示 | ビルドログを Claude チャットへ |

| キャッシュが残っている | シークレットウィンドウで確認 | ハードリロード |

**ビルド失敗時の対処**は、前回記事の H2-4 つまずき⑤(Vercelビルド失敗)で詳しく書いた通りです。「ビルドログを Claude チャットに全文渡して、原因を特定してもらう」**この一連の流れは、何度使っても安全な対処パターン**です。

### Vercel の自動デプロイの仕組み

**ここで、Vercel が何をしてくれているかを簡単に整理しておきます。「魔法のように本番反映される」のではなく、ちゃんとした仕組みがあります。**

Vercel の自動デプロイは、次のような流れで動いています。

1. **GitHub への push を検知**:GitHub から「変更があったよ」という通知が Vercel に飛ぶ
2. **コードを取得**:Vercel が最新のコードをダウンロード
3. **ビルドを実行**:`npm install` → `npm run build` を自動実行
4. **エラーチェック**:ビルドが成功したかを確認
5. **本番反映**:成功なら新しいバージョンを本番URLに反映、失敗なら通知

この一連の処理が、私が GitHub に push してから**1〜3分**で完了します。前回記事の H2-2 で「Vercel = 出版・配送センター」と比喩しましたが、その配送センターが**24時間自動運転**で動いている。これが現代のWeb公開の姿です。

> 【哲学】**「公開作業」という大げさな概念がなくなった**のが、Vercel の本質です。昔は、サーバーに FTP でファイルをアップロードして、設定を確認して、と何時間もかかった作業が、今は「git push」の一語で済む。**「文章を保存する感覚で本番が更新される」**のは、技術の歴史の積み重ねの結果です。

### 「作業ログ」を残す価値は何か?

**今日の作業を時系列で振り返って、Markdown ファイルにまとめる作業に入りました。これは「**今日の自分から、未来の自分への手紙**」です。**

| つまずいた箇所と原因 | 同じ問題を二度と踏まないため |
| 使ったプロンプトの抜粋 | 再利用できる「型」として保存 |
| 想定外の出来事 | 後で記事化する時のネタ |

私が今日まとめた作業ログは、約16,000字になりました。これだけの分量を残すのは大変に感じるかもしれませんが、**実は Claude にまとめてもらえば30分で完成**します。

このプロンプトを送れば、Claude が**今日のチャット履歴を構造化して**、立派な作業ログにまとめてくれます。**自分で書くより、客観的に整理できる**のが Claude に頼む利点です。

### 「マニュアル」を作る意味は何か?

**作業ログとは別に、「次回30分で済むマニュアル」を作りました。これは作業の手順を定型化することで、2回目以降の効率を劇的に上げる仕組みです。**

マニュアルと作業ログの違いを表で整理します。

| 観点 | 作業ログ | マニュアル |
|---|---|---|
| 視点 | 過去 | 未来 |
| 構成 | 時系列 | 手順順 |
| 含むもの | 出来事・つまずき・感想 | 手順・チェックリスト・コピペ用テンプレ |
| 想定読者 | 未来の自分 | 未来の自分(または他の人) |
| 文字数 | 多い(細かく書く) | 少ない(要点だけ) |
| 使うタイミング | 振り返る時 | 同じ作業を再開する時 |

私のマニュアルは、約6,600字でした。作業ログ(約16,000字)よりも大幅にコンパクトです。**「あの時の自分が必要としていた手順」だけに絞る**ことで、再利用しやすくなります。

> 【哲学】月次サロンで参加者によく言うのは、「**学んだら、必ず形に残してください**」です。学びを記憶だけに頼ると、3週間後には半分忘れています。Markdown でも、手書きノートでも、形は何でもいい。**「これを後で見ても、自分が分かる状態」**にする。これが、AI 時代の学習者の基本姿勢だと思っています。

### マニュアルを書く時のコツ

**マニュアルを書く時、つい「網羅的に書こう」と力が入ります。でも、それだと書き終わらず、結局使わないマニュアルになります。コツは「**最小限から始める**」ことです。**

マニュアルを書く時の私の方針を整理します。

#### 方針1:1回目の作業を、なぞるだけにする

最初のマニュアルは、「今日の作業をそのままなぞる」だけで十分です。最適化は2回目以降の経験を経てから加えます。**完璧主義を避ける**のが、書き終えるための一番の秘訣です。

#### 方針2:時間目安を必ず入れる

各ステップに「○分」と時間目安を入れます。これがあると、**作業全体の見通し**がつきます。「これから30分の作業に入る」と分かると、心理的なハードルが下がります。

#### 方針3:コピペ用のプロンプトを残す

Claude Code に投げる依頼プロンプトは、必ずコピペできる形でマニュアルに含めます。**毎回ゼロから考えない**で済むのが、マニュアルの最大の価値です。

#### 方針4:つまずきポイントは「想定される異常系」として残す

今日遭遇したつまずき(404エラー、自動コミット問題、未コミット10件)は、マニュアルの末尾に「想定される異常系と対処」として整理します。**同じ問題に二度遭遇した時、対処法がすぐ見つかる**ようにする。

## なぜ「悩んだらチャット、手を動かすときはCode」が機能するのか?

**ここまで7つのステップを振り返ると、ある共通パターンが浮かび上がります。「考えるとき」と「動くとき」を分ける。これが、非エンジニアの私にとって最も安全で、最も効率的なAIの使い方でした。**

朝6時24分から始まった作業を、朝9時56分の本番反映確認まで、約4時間で完了しました。振り返ると、各ステップで毎回同じパターンを繰り返していたことに気づきます。**Claude チャットで考えて、Claude Code で動く**。この行き来が、作業全体を貫く一本の軸でした。

ここでは、なぜこの使い分けが機能するのかを、もう一段深く整理します。技術論ではなく、**態度論**として伝えたい話です。

### なぜ「考えるとき」と「動くとき」を分けるのか?

**ひとりで作業していると、考えながら手を動かしてしまいます。エラーが出たら、頭で原因を考えながら、画面のボタンを連打してしまう。これは、シニア向け講座で何度も見てきた失敗パターンでした。**

「考える」と「動く」を分けないと、何が起きるか。具体例を3つ挙げます。

#### 例1:画面が変だと感じた瞬間に、ボタンを連打する

これは月次サロンで頻繁に目にする光景です。スマホの画面に何かが表示されて、参加者の方が「変だ」と感じる。すると、慌てて画面を何度もタップする。同じボタンを5回押す。設定画面に入って、何が原因か分からないままスイッチを切り替える。

結果、最初の問題は解決しないどころか、**新しい問題が3つも追加されている**状態になります。原因は、**「考える」と「動く」が混在している**ことです。考えながら動くから、何を変えたか自分で把握できなくなる。

#### 例2:エラーメッセージを読まずに、回避策を試す

技術作業でも同じことが起きます。エラーが出た時、メッセージをじっくり読まずに「とりあえず再起動」「とりあえず別の方法」と試す。問題が解決すれば**「何が原因だったか分からないまま結果オーライ」**、解決しなければ**「もっと深い問題に踏み込む」**。

エラーメッセージは、ほとんどの場合、原因のヒントを含んでいます。読まないことで、自分で問題を悪化させてしまう。

#### 例3:途中まで書いた依頼を、確認せずに送る

Claude Code への依頼でも起きます。プロンプトを途中まで書いて、「まあいいか」と送ってしまう。すると、Claude Code は私が**伝え忘れた前提**を勝手に補って作業を始める。後で結果を見ると、「**そうじゃない**」と気づく。でも、もう編集は終わっている。

3つの例に共通するのは、**「考える時間を惜しんで、すぐに動いた」**ことです。動く前に1〜2分、状況を整理する時間を取れば、3つとも防げました。

### Claude チャットを「考える時間」の容器として使う

**「考える時間」を意識的に作るのは、思った以上に難しいです。大人になると、「待つこと」「立ち止まること」が苦手になります。Claude チャットは、その「考える時間」の容器として機能します。**

なぜ Claude チャットが考える時間の容器になるのか。3つの仕組みがあります。

#### 仕組み1:文字を打つ作業が、自然に手を止める

Claude チャットに状況を伝える時、私は手を止めて、文字を打つ作業に専念します。**この「手を止める」だけで、判断ミスが激減します**。

文字を打つ作業は、頭の中の混乱を整理する時間です。「いつ、どこで、何が、どう起きたか」を順番に書き出す。書きながら、自分の頭の中も整理されていく。**書く前と書いた後では、状況の見え方が違う**ことが多いです。

#### 仕組み2:相手に伝える前提で書くことで、客観視できる

Claude チャットに状況を伝える時、相手に分かるように書く必要があります。**「自分にだけ分かる省略」が許されない**。

これが効きます。月次サロンで参加者に「困ったら、まず友人に LINE する文章を作る感覚で、AI に状況を伝えてください」と教えています。**他人に説明しようとする瞬間に、客観性が生まれる**。これは AI に限らず、人間との対話でも同じ効果があります。

#### 仕組み3:返事が返ってくる前に、自分で答えに辿り着くことがある

Claude チャットに状況を書いて、送信ボタンを押すまでの間に、**「あ、これかも」と自分で原因に気づく**ことがあります。**書く作業自体が、思考を進める**からです。

これは「**ラバーダック・デバッグ**」と呼ばれる、プログラマーの世界の有名な手法です。机の上のゴム製のアヒルに向かって問題を説明すると、自分で答えを見つける、というユーモラスな話。Claude チャットは、答えてくれるアヒル、と言えます。

### Claude Code を「動く時間」の起点として使う

**「動く時間」は、計画が固まってからスタートします。Claude Code は、その動きを実行する起点として機能します。ここで大事なのは、**Claude Code を起動する前に、計画が完成している**ことです。**

なぜ Claude Code を起動する前に計画を完成させるのか。理由は3つあります。

#### 理由1:Claude Code は実行する力を持つ

Claude チャットと違い、Claude Code は**ファイルを実際に変更する力**を持ちます。これは強力ですが、同時に**取り返しがつかない動きをする可能性**を意味します。

計画が固まらないまま Claude Code に依頼すると、私が想定していなかった編集が起きる可能性があります。**実行力があるツールには、実行前の準備で慎重さが必要**です。

#### 理由2:Claude Code との対話は短くしたい

Claude チャットでの対話は、**長くなっても問題ありません**。考える作業は、何往復もしながら整理していくものです。「これは何ですか?」「では、こう考えるのはどうですか?」「いや、それより…」という対話の往復が、思考を深めます。

一方、Claude Code との対話は、**できるだけ短く明確に**しておきたいです。「この計画通りに実行してください」**1ターン、長くて2〜3ターンで済ませる**のが理想です。実行の往復が増えるほど、ファイルの状態が複雑になります。

#### 理由3:計画があれば、検収条件が決まる

事前に計画を立てておくと、**「実行後に何を確認すればOKか」**が決まります。これが Step B-2 で書いた「**作業前に検収条件を決める**」テクニックです。

Claude Code に「この5行を削除して、次の3つを報告してください」と頼めば、報告内容を見るだけで成功か失敗か判断できます。**計画なしで実行を頼むと、結果を見ても「これで合っているのか」が分からない**のです。

### 7ステップで実演された「考える/動く」の使い分け

**今日の7ステップを通して、「考える」と「動く」がどう使い分けられたかを表で振り返ります。**

各ステップで、Claude チャットと Claude Code の使い分けを並べてみます。

| ステップ | Claude チャットを使った場面 | Claude Code を使った場面 |

| Step B-1(同期と整理) | 未コミット10件の正体相談、移動先の方針相談 | (なし。手動でファイル移動) |
| Step B-2(リンク死削除) | (なし) | リンク死5本の削除実行 |

### この使い分けが「安全」を生む3つの仕組み

**「考えるとき」と「動くとき」を分ける使い分けは、単に効率が上がるからではなく、**「何が起きるか分からない作業」を「何が起きるか分かる作業」に変えてくれる**から大事です。これが非エンジニアにとっての最大の安全装置です。**

ひとりで作業していると、考えながら手を動かしてしまいます。Claude チャットに状況を投げる時、私は手を止めて、文字を打つ作業に専念します。**この「手を止める」だけで、判断ミスが激減します**。

Claude Code は、依頼を受けると「これからこれをします」と計画を提示してくれることが多いです。これは、ひとりで作業していたら絶対に得られない情報です。**実行前に内容が分かる**というのは、技術作業における安心感の本体です。

#### 仕組み3:エラー時に「何が起きたか」を共有できる

エラーが出た時、Claude チャットに状況を伝える時、私は自分で言語化します。**「いつ、どこで、何が、どう起きたか」**を文字にする。この作業をするだけで、自分の頭の中も整理されます。Claude が答えを返す前に、自分で気づくこともあります。

## よくある質問(FAQ)

ここまで読んでくださった方が、まだ持っているかもしれない疑問に、まとめてお答えします。今回の記事特有の疑問に絞って、6問を選びました。

### Q1. Claude Code が自動でコミットしてしまうのを防ぐにはどうしたらいいですか?

**A. 依頼プロンプトの中で「git add や git commit は実行しないでください」と明示的に指示すれば、Claude Code はファイル編集だけに留まってくれます。**

具体的なプロンプト例:

```
【作業の範囲】
ファイル編集のみお願いします。
git add や git commit は実行しないでください。
コミットは私が自分で確認してから実行します。
```

これを依頼の冒頭または末尾に1行追加するだけで、コミット作業のコントロール権を取り戻せます。

なぜこれが大事かというと、**自分で commit メッセージを書く機会を持つほうが、Git の理解が深まる**からです。便利さよりも、自分の理解と判断の機会を優先する。前回記事の H2-2 で書いた「**作品の所有権は、最後まで人間の側にある**」の応用形です。

### Q2. 404 が出た時、最初に試すべきことは何ですか?

**A. 順番が大事です。「ハードリロード → サーバー再起動 → ブラウザ変更」の順で試してください。サーバー再起動が9割の問題を解決します。**

順番に意味があります。

| 順番 | 試すこと | 直る原因 |
|---|---|---|
| ① | ハードリロード(Cmd + Shift + R) | ブラウザキャッシュ |
| ② | ローカルサーバーを再起動 | Astro ビルドキャッシュ(層③) |
| ③ | シークレットウィンドウで開く | ブラウザ全体のキャッシュ |
| ④ | 別のブラウザで開く | ブラウザ固有の設定問題 |

特に**「URL構造を変える変更」**(`getStaticPaths` 変更、新ルート追加、設定ファイル変更)を行った後は、まずサーバー再起動を試してください。これで多くの 404 は解決します。

詳しい仕組みは H2-6 で書いた「変更が反映されない5つの層」を参照してください。

### Q3. マニュアルがあっても、実際には30分で終わらないかもしれない時の対処法は?

**A. 「30分」という数字は目安です。最初の数回は1〜2時間かかっても問題ありません。大事なのは、毎回少しずつ早くなっていくことです。**

時間が伸びる原因と対処を整理します。

| 原因 | 対処 |
|---|---|
| 想定外の事態が起きる | 慌てず Claude チャットに状況を共有 |
| メタ情報を決めるのに迷う | 過去記事のフロントマターをコピペして変更 |
| プレビュー確認に時間がかかる | チェックリストを作っておく |
| 後始末・ログ作成の時間 | 別日に回しても OK |

**「30分」は理想形ですが、必達目標ではない**ことを覚えておいてください。記事の H2-9 で書いた「最初から完璧を目指さない」「動くものを優先」の精神は、マニュアル運用にも当てはまります。

毎回作業時間を記録しておくと、自分の上達が見えて楽しいです。

### Q4. 既存の「準備中」記事を本文化するには、同じ手順で進められますか?

**A. はい、ほぼ同じ手順で進められます。「新記事を追加する」のと「既存の準備中記事を本文化する」の違いは、Step B-3 の作業内容だけです。**

違いを表で整理します。

| 工程 | 新記事追加 | 既存記事の本文化 |
|---|---|---|
| Step B-1(同期確認) | 同じ | 同じ |
| Step B-2(整理) | 必要に応じて | 不要な場合が多い |
| Step B-3(編集) | getStaticPaths追加+本文ブロック追加+一覧追加 | **本文ブロックの追加だけ** |
| Step B-4(プレビュー) | 同じ | 同じ |
| Step B-5(GitHub) | 同じ | 同じ |
| Step B-6(本番確認) | 同じ | 同じ |
| Step B-7(振り返り) | 同じ | 同じ |

つまり、本文化の方が**作業範囲が小さい**ので、より早く終わる可能性が高いです。私のサイトには現在2本の「準備中」記事(salon-ai-hajimete / notebooklm-mcp-cli)があるので、これらを本文化する作業を、次回マニュアル検証として実施する予定です。

### Q5. Content Collections に移行するタイミングはいつですか?

**A. 記事数が10本を超えるか、毎月3〜5本のペースで更新する見込みが立った時が、移行の検討タイミングです。それまでは現状方式で十分です。**

判断基準を表で整理します。

| 状況 | 推奨される対応 |
|---|---|
| 記事が5本未満、月1本ペース | 現状方式(`[slug].astro` 直書き)で十分 |
| 記事が5〜10本、月2〜3本ペース | 移行を計画段階で検討開始 |
| 記事が10本以上、月3本以上ペース | 移行を実施するタイミング |

なぜすぐ移行しないかというと、**今の作業負担と将来の作業負担を天秤にかけている**からです。Content Collections 化には2〜4時間の作業が必要です。記事が少ないうちにやっても、メリットを実感する機会が少ない。**「3つのファイルを毎回更新するのが本当に面倒だ」と感じてから移行する**のが、私には合っています。

これは記事 H2-9 の「最初から完璧を目指さない」「動くものを優先」の精神です。

### Q6. シニア向けに教える時、どこから伝え始めるのがいいですか?

**A. 「悩んだらチャット、手を動かすときはCode」の使い分けから伝えるのが、私のおすすめです。技術より先に「態度」を学んでもらうほうが、学習効果が高いです。**

シニア向けに伝える時の順序を、私なりに整理します。

#### ステップ1:「考えるとき」と「動くとき」を分ける感覚を身につける

最初は技術抜きで、**日常生活の中で「考える時間」と「動く時間」を分ける練習**をしてもらいます。例えば、買い物で迷った時、まず紙に書いて整理してから決める。これだけで、AI を使う時の態度の半分は身につきます。

#### ステップ2:Claude チャットで「状況を伝える」練習をする

Claude チャットに、自分のスマホで困った状況を伝える練習をします。「画面が変だ」ではなく、「3日前から、メールアプリで送信ボタンを押すとエラーが出ます。エラーメッセージは『接続できません』です」と具体的に書く練習。

#### ステップ3:Claude Code はまだ使わない

シニア向け教室では、私自身も Claude Code を使わせない方針です。**Claude Code はファイル変更の力があり、操作ミスのリスクがある**ため。代わりに、Claude チャットの活用に集中してもらいます。

#### ステップ4:興味のある人だけ、次の段階に進む

サイトを作ったり、Claude Code を使ったりするのは、**興味のある人だけ**です。全員に強制しない。前回記事の H2-6 で書いた「興味の温度差を尊重する」という方針です。

> 【哲学】月次サロンで全員に「サイトを作りましょう」とは言わないのと同じです。**選択肢を提示することと、選ばせることは違います**。私の役割は前者であって、後者ではない。これがシニア教育の現場で一番大事な姿勢です。

## まとめ:あなたも次は30分でサイトを更新できる

ここまでお読みいただき、ありがとうございました。最後に、この記事の要点を3つに絞ります。

**1. 「悩んだらチャット、手を動かすときは Code」を実践すると、サイト公開作業は安全に進む**

非エンジニアにとって、AI の使い分けは技術論ではなく、態度論です。考える時はチャット、動く時はCode。この行き来が、安全と効率の両方を支えてくれます。

**2. 「探検 → 計画 → 実行」の3段階パターンを覚えると、複雑な作業も乗り越えられる**

Claude Code に複雑な作業を頼む時は、いきなり実行を頼まないこと。まず探検で現状を把握し、計画を見せてもらい、OK返事をしてから実行する。**この3段階で、不可逆な失敗のほとんどを防げます**。

**3. 一度経験すれば、次回は半分以下の時間で済む**

今日の作業に約4時間かかったのは、「学びながら進めた」からです。マニュアル化と作業ログを残しておけば、次回は30分前後で完了できる見込みです。**経験を資産に変える**のは、学びを書き残すことから始まります。
